工具 - Codex 账号切换器

一条命令切换机器上的 Codex 全局身份，顺带看清每个账号还剩多少额度、什么时候重置、手上有几张重置卡。 本文覆盖部署、日常用法、脚本架构，以及你要改它时该动哪里。

脚本 codex-switch · bash · 1052 行 实测 codex-cli 0.149.1 / 0.153.4 平台 Linux · 单机单用户

00 它解决什么

Codex CLI 到今天为止没有原生的多账号管理：codex login 只有一个 status 子命令， --profile 切的是模型配置而不是身份。想换账号只能重新登录一次，换回来再登一次。

这个脚本把「登录态」当成可存档的槽位来管：每个账号登录一次就被记住，之后 codex-switch 2 一条命令切过去， 新开的终端、重启后的 VS Code 插件都跟着走。顺带把额度信息也查出来了 —— 毕竟切账号的动机通常就是「这个用完了」。

$ codex-switch list 槽位 账号 套餐 剩余额度 重置 重置卡 状态 ───────────────────────────────────────────────────────────────────────── 1 alice@example.com pro ▓░░░░░░░░░ 1% 2h15m 后 3 正常 * 2 bob@example.com pro ▓▓▓▓▓▓▓▓▓▓ 99% 6d23h 后 3 正常 * = 当前账号 · 额度缓存于 3m 前 · codex-switch list --live 实时刷新

剩余额度 ≤10% 标红、≤30% 标黄。额度、重置时间、重置卡数量都来自官方接口，不是估算的。

01 环境前提

部署前先对齐这几项，尤其是第二条 —— 不满足的话切换会静默无效。

项目要求怎么确认
Codex CLI 0.149 以上 codex --version
凭据存储模式 必须是 File，不能是 keyring codex doctor | grep "storage mode"
命令行依赖 jq python3 flock sha256sum awk install mktemp 脚本启动时自检，缺哪个报哪个
PATH ~/.local/bin 在 PATH 里 echo $PATH | tr : '\n' | grep local/bin
凭据存储模式是硬前提 Codex 支持把凭据存进系统 keyring。如果是 keyring 模式，脚本切 auth.json 完全不起作用 —— 文件换了，Codex 照样读 keyring 里的旧身份。必须先切成文件模式。

如果 codex doctor 显示的不是 File，在 ~/.codex/config.toml 顶部加一行，然后重新登录一次让凭据落到文件：

# ~/.codex/config.toml 第一行 cli_auth_credentials_store = "file" # 然后重新登录，让凭据写进 auth.json $ codex logout && codex login

jq 和 python3 来自系统还是 conda 都行，脚本不挑。Python 只用了标准库，3.6 以上即可。

02 部署

  1. 放置脚本

    把 codex-switch 文件放进 ~/.local/bin/ 并加执行位。

    $ install -m 755 codex-switch ~/.local/bin/codex-switch $ command -v codex-switch # 应该打印路径

    如果 ~/.local/bin 不在 PATH，往 ~/.bashrc 加 export PATH="$HOME/.local/bin:$PATH"。

  2. 登记当前账号为槽位 1

    这一步只是把现有的登录态存个档，不会改动任何凭据，安全。

    $ codex-switch adopt 1 已把当前账号登记为槽位 1。

  3. 加第二个账号

    这一步会打开登录流程。远程机器（SSH / VS Code Remote）用 --device-auth 走设备码，不需要本机浏览器。 登录成功后自动切过去，不用再单独切一次。

    $ codex-switch add 2 --device-auth

    如果此时有 Codex 在跑，脚本会在切换完成后自动终止它们（它们持的是旧账号凭据）， 不需要你手动关。原因见第 05 节。

  4. 验收

    $ codex-switch list --live $ codex-switch status

    status 显示 consistent 就说明槽位记录和实际登录态一致。

03 日常用法

命令作用
codex-switch 2切到槽位 2（use 2 是同义写法）
codex-switch list列出所有槽位，额度读本地缓存，秒回
codex-switch list --live联网实时查所有槽位额度，约 2.5 秒/账号
codex-switch status槽位一致性 + codex login status + 额度表
codex-switch add N登录新账号存进槽位 N 并切过去
codex-switch adopt N把当前 auth.json 登记为槽位 N（不触发登录）
--keep-running切换后不终止旧进程（它们会继续用旧账号，有覆盖风险）
--no-color禁用彩色（管道输出时自动禁用，无需手动加）
切换后 VS Code 仍需 Reload Window Codex 只在进程启动时加载一次认证，协议层没有凭据热重载接口。脚本会自动终止持旧凭据的进程， 但 VS Code 插件不会自己重连 —— 需要 Ctrl+Shift+P → Developer: Reload Window （实测：kill 掉 app-server 后插件不会自动重拉，要一次交互才会）。新开的终端则立刻是新账号。

04 脚本架构

要改它，先知道它怎么组织的。整体是「bash 管文件与安全，内嵌 Python 管信息与渲染」。

核心思路

Codex 的全局身份就是 ~/.codex/auth.json 这一个文件。脚本把每个账号的这份文件存成槽位快照， 切换 = 把当前的存回原槽位，再把目标槽位的复制过来。因为改的是默认路径而不是设置 CODEX_HOME，所以切换对所有 Codex 客户端全局生效，不需要给每个账号配一套启动别名。

磁盘布局

~/.codex/ ├── auth.json # 当前生效的身份（Codex 读这个） ├── config.toml # 需含 cli_auth_credentials_store = "file" └── account_storage/ ├── acc1.json # 槽位 1 的凭据快照 ├── acc2.json # 槽位 2 ├── current # 当前槽位号 ├── switch.lock # flock 互斥锁 ├── pending.json # 切换事务记录，中断后可恢复 └── usage/accN.json # 额度缓存（含账号指纹）

安全机制

这几层是脚本里最不该随手改的部分，每一层都对应一个真实会踩的坑：

机制实现防什么
互斥锁 flock 全局独占 两个切换同时跑，凭据写花
原子替换 mktemp + mv -fT 写一半被打断留下残缺凭据
身份指纹 sha256(account_id) 绕过脚本手工登录后，把 A 账号覆盖进 B 槽位
事务记录 pending.json + 启动时恢复 切换中途被 kill，状态卡在中间
旧进程清理 按启动时刻识别 + SIGTERM + 复查指纹 旧进程继续用旧账号、并把旧凭据刷回来（见 05 节）

指纹只取 account_id，不含 token 值 —— 所以 token 刷新后指纹不变， 「同一个账号」和「同一份 token」被刻意区分开了。

信息层

额度这类信息分两个来源，成本差一个数量级：

信息来源成本
邮箱 · 套餐 · 订阅到期 · token 有效期本地解 auth.json 里的 JWT payload离线，零成本
剩余额度 · 重置时间 · 重置卡codex app-server 的 JSON-RPC account/rateLimits/read联网，~2.5s

第二条是唯一可行通道 —— REST /backend-api/* 对 codex token 一律 403，响应头不带额度， codex exec --json 只给单次 turn 的 token 计数，本地 sqlite 也没有缓存。 完整方法表可以自己导：codex app-server generate-json-schema --out /tmp/schema。

05 三个必须知道的坑

都是实测撞出来的，不是理论推演。改脚本前尤其要理解第一条。

refresh_token 是一次性轮换的

OpenAI 的 refresh_token 用一次就作废，换回来一个新的。这意味着任何把槽位快照复制到别处去用的操作， 都必须把刷新后的凭据写回槽位文件，否则那个账号直接登出，再登录时报：

401 refresh_token_reused "Your refresh token has already been used to generate a new access token."

脚本查非活跃槽位额度时就走这条路：复制到隔离的临时 CODEX_HOME → 查询 → 用 sha256 检测凭据是否被刷新 → 指纹校验确认还是同一个账号 → 写回槽位。如果你要加任何「拿槽位凭据去做事」的功能，必须照抄这套写回逻辑。

旧进程既读不到新账号，还可能写回旧凭据

Codex 只在进程启动时加载一次认证。切换 auth.json 对已经在跑的进程毫无影响 —— 它会一直用启动那一刻的账号，直到重启为止。

这是真实发生过的一次事故，时间线完整对得上：

09-01 11:28 app-server 启动，加载账号 A 的凭据 09-07 11:09 auth.json 切换成账号 B（还剩 99% 额度） 09-07 12:08 VS Code 里的 Codex 报错："已达到使用上限，13:32 再试" 而账号 A 的额度重置时刻正好是 13:32:48 → 那个跑了 6 天没重启的 app-server 全程用的是账号 A， 切换到账号 B 完全没作用到它身上。

更隐蔽的是第二重风险：旧进程可能在任意时刻用旧账号的 refresh_token 换新 token 并写回 auth.json —— 你切的新账号被静默覆盖，同时旧账号的槽位快照因 token 被轮换而失效。 实测过一次进程启动 5 分钟后就主动刷新凭据的情况，当时旧 token 明明还有 4 天才过期， 刷新时机完全不可预测。

脚本现在会自动处理 切换完成后自动终止「启动时刻早于 auth.json 写入时刻」的 Codex 进程 —— 这个判据精确地 对应「持旧凭据」，切换后才启动的进程不会被误伤。终止后还会复查一次指纹，确认没有旧进程 抢在中间把凭据写回。风险窗口从「无限期」压到几百毫秒。

进程检测只看自己

running_codex_pids 用的是 ps -u $(id -u)，只数当前 Unix 用户的进程。 多人共用的机器上不会被别人的 Codex 误伤 —— 但反过来，同一用户在别的终端跑着的 Codex 也是会拦你的。

06 定制指南

脚本是单文件的，改完直接生效，没有构建步骤。下面按「想改什么 → 动哪个函数」列出常见改法。 建议改之前先 cp ~/.local/bin/codex-switch{,.bak}，改完 bash -n 过一遍语法。

换个地方存数据

所有路径都从脚本头部 4 行常量派生，且 base 支持环境变量覆盖 —— 想拿一份隔离的数据做实验， 不用改代码：

# 脚本头部 BASE_DIR="${CODEX_SWITCH_HOME:-$HOME/.codex}" STORE_DIR="$BASE_DIR/account_storage" USAGE_DIR="$STORE_DIR/usage" # 拿个沙箱跑，完全不碰真实凭据 $ CODEX_SWITCH_HOME=/tmp/cxtest codex-switch list

改显示

渲染全在内嵌的 Python 辅助器里（py_helper() 函数体内），改这几处就够：

render() → heads / keys

表格有哪些列、列名叫什么。两个数组一一对应，同步改。

_bar(remain, width=10)

额度条的字符和宽度。当前用 ▓░ 十格，还剩一点点时至少点亮一格，避免和「耗尽」混淆。

render() 里的配色阈值

当前剩余 ≤10% 红、≤30% 黄。ANSI 码：31 红、33 黄、32 绿、2 暗、1 粗。

_rel(ts)

相对时间的说法，现在是「3h23m 后」。想要绝对时间戳就改这里。

_pick_window(rl)

服务端可能同时给周窗口和 5 小时窗口，当前取已用比例更高的那个（先撞到的）。想固定看某个窗口就改判据。

decode(path)

从 JWT 里多解些字段出来。id_token 里还有订阅起止时间、组织信息、认证方式没用上。

加新的信息源

同一个 app-server 通道上还挂着别的方法，加进来的成本很低 —— 照着 fetch() 换个 method 就行：

方法能拿到
account/usage/read 累计 token、单日峰值、最长单次 turn、连续使用天数、按天的用量序列
account/read 邮箱与套餐（本地 JWT 已能解出，一般用不上）
account/rateLimitResetCredit/consume 消费重置卡，立即重置额度窗口。要带 idempotencyKey（建议 UUID）， 返回 reset / nothingToReset / noCredit / alreadyRedeemed
最后一个是写操作 当前脚本刻意只读不消费重置卡。要加的话建议配二次确认，并注意 idempotencyKey 在重试时必须复用同一个值，否则会连消费两张。

调整进程处理策略

切换后自动终止旧进程这套逻辑在 stale_codex_pids() 和 restart_stale_clients() 两个函数里。识别判据是 进程启动时刻 < auth.json 写入时刻，用 ps -o etimes= 拿运行秒数换算，比解析 lstart 的日期字符串稳。

进程名用 comm 精确匹配 codex 和 codex-code-mode*， 不要改成匹配 args —— 那样会把 codex-switch 自身和 检查命令一起算进去，脚本会杀掉自己（这个坑踩过）。ps -u $(id -u) 限定只看当前用户， 共享机器上不会误伤别人的 Codex。

想保留旧进程用 --keep-running，但要清楚代价：那些进程继续用旧账号， 并且可能把旧凭据写回。

不要动的部分

atomic_auth_copy、fingerprint_auth、recover_pending、 fetch_usage_slot 的写回段 —— 这四处是凭据安全的地基，改错的后果是账号登出或槽位互相覆盖， 而且往往是静默的，等你发现时已经登不上了。

07 边界

说清楚它不管什么，省得踩空：

作用范围同一台机器、同一个 Unix 用户、默认 ~/.codex。另一台机器 / WSL / Dev Container / 别的用户各有各的，要分别部署
热切换协议层不支持。脚本用「终止旧进程」来逼近：CLI 下次启动即新账号，VS Code 需 Reload Window
登录方式ChatGPT 登录和 API key 都能存槽位；--with-access-token 那种没有 refresh 能力的形式被显式拒绝
额度数据来自服务端实时接口，非活跃槽位显示的是缓存值，带时间戳标注
实测环境 Ubuntu 20.04 · codex-cli 0.149.1 → 0.153.4 · bash 5.0 · python 3.11 · jq 1.6
脚本随 Codex 版本演进可能需要跟进，最容易变的是 app-server 的 JSON-RPC 方法名， 用 generate-json-schema 导出对照即可。
