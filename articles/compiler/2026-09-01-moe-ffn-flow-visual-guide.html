Lesson 0 · 先建立一句话心智模型

MoE FFN = 很多个 Dense FFN + 按 token 选择 + 加权合并

先不看 index、不看并行、不看硬件。只比较一个 token 在 Dense FFN 和 MoE FFN 中分别经历什么。

前置知识：只需 Dense FFN
你已经会的 Dense FFN
token x → 同一个 FFN → y

所有 token 都走同一套权重。模型容量和每个 token 的计算量绑在一起。

把 1 个 FFN 复制成 E 个 + 每个 token 只选 K 个
MoE FFN
token x → Router → E₁ + E₃ → y

Router 挑出少数专家；每个专家仍然只是一个普通 FFN；最后按权重把多个结果合成一个 y。

第一条记忆： Expert 不是神秘的新算子，它就是一套独立权重的 Dense FFN。

01
Dense FFN recap

先确认：一个 Expert 内部，算的还是你熟悉的 FFN

下面四步对 Dense FFN 和每一个 routed/shared expert 都成立；不同 expert 只是在使用不同的权重。

输入 x [H]
→
两条线性投影 gate = xWgate
up = xWup [H] → [I]，宽度被展开
→
SwiGLU SiLU(gate) ⊙ up [I]，逐元素门控
→
Down Projection act · Wdown [I] → [H]，回到 hidden
把它复制 E 份

结构相同，权重不同

MoE 不让所有 expert 共用一套 Wgate/Wup/Wdown。每个 expert 都有自己的三套权重，因此能学习不同模式。

Expertₑ(x) = Wdownₑ · (SiLU(xWgateₑ) ⊙ xWupₑ)
Expert 0FFN 结构权重 W⁰
Expert 1FFN 结构权重 W¹
Expert 2FFN 结构权重 W²
Expert 3FFN 结构权重 W³
通俗类比

Dense FFN 像一家店只有一个全能厨师；MoE 像有很多厨师，菜谱结构相同，但各自学到的手艺不同。

02
Why mixture of experts

为什么不直接把一个 Dense FFN 做得更大？

核心目的不是“省掉 FFN”，而是让模型拥有很多参数，同时让一个 token 只激活其中少数参数。

等参数量的大 Dense

8 份容量，8 份都要算

把 Dense FFN 直接放大，参数增加的同时，每个 token 的矩阵计算也一起增加。

VS
MoE · E=8, Top-K=2

存 8 份容量，每个 token 只算 2 份

理想化地看，expert 参数有 8 份，active expert compute 只有 2 份，另加 Router、调度和通信开销。

容量更大

不同 expert 可以存下不同模式，模型总参数量随 expert 数量增长。

计算保持稀疏

每个 token 只走 Top-K 个 expert，不需要把所有 expert 都执行一遍。

按 token 条件计算

不同 token 可以选择不同 expert，计算路径随输入变化。

但不是免费午餐Router 可能选不均匀
新增系统问题token 必须 dispatch / combine
分布式代价expert 权重和 token 可能跨设备
硬件执行问题不同 expert 的小批量需要重新分组
第二条记忆： MoE 的价值是总容量看 E，单 token 计算看 K；通常 K ≪ E。

单卡故事懂了以后，TP / EP 只是“东西太大，需要分开放”

TP：一个 expert 太宽，把它的 intermediate 维 I 切给多个 rank；大家算同一个 expert 的不同片段，最后求和。

EP：expert 太多，把 expert 集合切给多个 rank；每个 rank 只负责自己拥有的 expert，remote route 记成 -1。

Zeus 双核：设备内部再拆一层工作，不改变 Router、route 和 expert 的数学定义。

Stable bucket + direct scatter-back

Index 是怎么从 Top-K 一路走到输出的

先用小 block 手算，再切到 EP global-to-local 例子，最后看 16B T4 的真实 B=64 布局。

global expert local bucket routing block

1Top-K 输出：token-major route table

topk_ids[t,slot] 是 global expert id；每个格子同时拥有唯一的 flat_idx = t×K+slot。

2Flatten：先给每条 route 一个永久编号

这个编号贯穿 Align、Grouped GEMM 和 Reduce；它不是普通 token id。

3Align：global-to-local，然后按 expert stable bucket

同一 expert 的 route 保持原输入顺序；EP rank 不拥有的 expert 统一进入 -1 remote bucket。

4输出四张 Grouped GEMM 执行表

默认公共 ABI 用 R=T×K 作为 padding sentinel；fused relaxed 路径可不写 padding，必须以 count 为准。

One name, one responsibility

Index 词典与排查口诀

看到 dump 或 trace 时，先判断它属于模型语义、路由身份、执行队列还是物理 weight slot。

名称 典型 shape / dtype 真正含义 谁产生 → 谁消费 常见误区
topk_ids [T,K] · int32 每个 token 选中的 global expert id Router/Top-K → Align 不是 local expert id，也不是 weight slot
topk_weights [T,K] · bf16 对应 route 的归一化 mixture weight Router/Top-K → final reduce correction bias 用于选择，不应直接混进 weight
flat_idx / q scalar integer q=t×K+slot，一条 route 的永久身份 Top-K layout → Align → GEMM → Reduce 它不是普通 token id
sorted_token_ids [max_padded] · fp32 ABI 按 expert 分桶后的 flat route ids Align → Grouped GEMM 名字像 token id，实际值是 route id
expert_ids [max_blocks] · fp32 ABI 每个 routing block 使用的 local expert/weight slot Align/cache remap → Grouped GEMM 一项对应一个 block，不是一项对应一条 route
block_valid_counts [max_blocks] · int32 每个 block 里真实 route 的数量 Align → strict-masked Grouped GEMM relaxed padding 下它才是有效 lane 的 source of truth
num_tokens_post_pad [1] · int32 所有 active buckets 对齐后的总 slot 数 Align → Grouped GEMM loop bound 不是实际 token 数，也不是实际 route 数
off_expert scalar int32 consumer 当前 block 的 weight-table offset 从 expert_ids load -1 是 deliberate remote-zero，不是随机坏数据
a_row_ids [GEMM_BLOCK_M] flat_idx // top_k，回到 hidden 的 token row Grouped GEMM 内部派生 同一个 token 的 K 条 route 会重复读取同一 hidden row
cumsum_buffer [num_bins+1] · fp32 ABI 每个 bin 的 padded prefix/end Align workspace/兼容输出 Grouped GEMM 主消费链不直接依赖它
