TritonShared - 标量 DMA 批量化

MoE T=4 每轮循环开头读四个 routing metadata 标量。硬件本可以让它们同时在飞，但中端把每个消费者钉在自己的 DMA 后面，CT 只能一个一个等。把 DMA 全部提到消费之前，每轮省约 500 cycle，全 kernel 22,517 → 20,012。

Triton kernel 写的四条 load

1off_a   = tl.load(expert_ids_ptr + block_a)
2count_a = tl.load(block_valid_counts_ptr + block_a)
3off_b   = tl.load(expert_ids_ptr + block_b, mask=has_b)
4count_b = tl.load(block_valid_counts_ptr + block_b, mask=has_b)

两个不同的入参指针、两个不同的下标 —— 四个地址互不相关，没有任何真实依赖。RTL 的 LD_CREDIT = 4 允许四条命令同时在飞，且小于 128 字节的搬运一律一个 beat，读 4 字节和读 24 字节同价。

先说清楚：同样是 tl.load，走的是两条不同的路

tensor 的 tl.load

a_tile = tl.load(a_ptr + …) → [4, 2048]

DRAM ──LD 搬运──▶ L2 ──▶PE / VP 直接消费

值就住在 L2，PE 从 L2 直接吃。IR 里这个 buffer 后面一条 memref.load 都没有 —— 不需要进寄存器。这是大家默认印象里的 tl.load。

标量的 tl.load

off_a = tl.load(expert_ids_ptr + block_a)

DRAM ──LD 搬运──▶ L2 暂存 16B ──CT 读 13cy──▶ 寄存器

多出 L2 → 寄存器这一跳，因为 off_a 要拿去算 weight 地址、count_a 要参与分支条件 —— 这些是标量控制流，必须在 CT 的通用寄存器里。而 CT 没有任何指令能直接读 DRAM，所以只能分两跳走。

判据是「这个值最终被谁消费」：被 PE/VP 消费就留在 L2；被 CT 消费就必须再搬进寄存器。所以下面时序图里突然冒出来的 CT，不是多余的一步，是标量路径的必需品 —— 也正是它把四条搬运串成了一条链。

③④ 带 mask 的那两条要多绕一步。mask=has_b 会把它们切进独立的 scf.if，而上提不允许跨越带 region 的 op —— mailbox 没有 tag，LD→CT 的 completion 按 FIFO 收，跨过 region 会让这条 mail 排到 region 内部所有 mail 前面而接收顺序不变，FIFO 就错位了（真在 zecl_custom_collective 上踩到过）。所以 pass 会先把同条件的相邻 scf.if 挪成紧邻，让上游 CombineIfs 把它们合并，之后 ③④ 才批得到一起。kernel 侧若把 mask 换成「下标 clamp + tl.where」，四条就落在同一 block，可以一次全批。
