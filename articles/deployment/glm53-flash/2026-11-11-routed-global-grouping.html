01

要改的是数据组织边界

当前 Routed 的窗口同时承担“识别专家”“缓存激活”“组成 M1/M2/M4”三件事。一旦扩大窗口，比较矩阵、FP8 cache 与在途中间值一起增长；容量紧张又迫使窗口缩小，导致同一专家跨窗口重复开组。继续只压 allocator 峰值或挪动几条指令，很难消除这一结构性损失。

建议路线：Router 生成可直接消费的专家索引，随现有一次 AllGather 传递；Routed 在全 batch 范围内合组，按需读取少量 hidden 行，用双槽 M4 执行。先保留现有权重、量化与 Reduce 数值语义，避免同时重做所有接口。

“NVIDIA 怎么做”在本文指 NVIDIA 硬件、CUTLASS，以及运行于其上的 vLLM、DeepGEMM、DeepEP 等公开实现；它们来自不同项目，不是同一条通用 kernel，也不代表所有 GPU MoE 都采用同一种布局。

容量在限制什么？

当前每核 512 KiB 的软件管理 L2/SRAM，需要容纳激活、控制 metadata、临时值和输出。单看 [T,4096] FP8 hidden cache，T32 / T40 / T128 就分别是 128 / 160 / 512 KiB。BS128 光这一项已经占满，还没有放任何中间结果。

源码中的 BS40 走 24 + 16 窗口，BS128 走 4 × 32。每个窗口重新读取、识别与合组，边界上有等待和 SRAM 复用。更大的 batch 本应带来更多同专家 token，但窗口把这些机会切开了。

这里的 L2 主要不是专家权重缓存。权重走既有 weight memory 路径；更多 token 合并，是争取一次权重遍历服务更多行。Zeus 的软件管理 L2/SRAM，与 NVIDIA GPU 的硬件 L2 cache 也不是同一概念。

03

NVIDIA GPU：全局排队，片上分块执行

Hopper 每个 SM 的 shared memory 只有官方标注的 228 KB，单 thread block 最大 227 KB。大 batch 的全部激活同样放不进去。GPU 将完整数据与索引保存在 global memory，SM 消费当前 tile；Hopper 的 TMA 等异步搬运机制帮助把供数与计算重叠。[Hopper Tuning Guide]

这些实现共同提供了一个可迁移的设计原则：全局关系先明确，计算只搬当前需要的块。Zeus 的 VP/CT、DMA、PE 与 CUDA 的 warp、扫描、原子操作及 TMA 不同，照搬 GPU 上的 prefix-sum + scatter 未必划算。需要沿用原则，再选择适合 Zeus 的索引格式。

一个容量算例：1 MiB 输入，不需要 1 MiB shared memory

以 BF16 的 [128,4096] 输入为例，完整输入是 1 MiB。若某个专家有足够行，示意地选 M_tile=64, N_tile=128, K_tile=128，一次只搬 A、B 的一个 K 段：

示意 tile计算容量
A：当前 64 行输入片段64 × 128 × 2 bytes16 KiB
B：当前专家权重片段128 × 128 × 2 bytes32 KiB
A + B 双缓冲2 × (16 + 32) KiB96 KiB
C：FP32 累加结果64 × 128 × 4 bytes，分散在寄存器等累加资源中32 KiB

沿 K 维遍历 32 段，完成这一块输出；其它 M/N 块继续调度。当前 B tile 同时服务这 64 行 A，形成权重复用；整 batch 与完整权重仍留在 global memory。这是基于分块 GEMM 的容量推导，不是某个实际 CUTLASS 配置或 occupancy 保证；真实 kernel 还受 MMA 形状、布局、barrier、epilogue 与寄存器限额约束。

分块与流水机制依据：CUTLASS · Efficient GEMM；上表形状与容量为本文示意计算。

大 batch 为什么有帮助，又为什么不会无限上涨？

同一个专家积累更多 token，可以填满更多计算 tile，减少尾块与重复权重遍历，并摊薄调度成本。但合组之后仍有权重供数、激活搬运、FFN 计算、输出归并和通信。先消除人为窗口带来的损失，再测自然带宽与算力上限。GPU 的这个设计不构成“BS 越大吞吐必然线性增长”的保证。

假设同一专家在前一窗口命中 t2、t9，在后一窗口命中 t25、t33。token 的内容与输出位置都不变，只改变分组范围。

两组 M2。窗口结束就提交尾组，同一专家需要两次 Gate / Up / Down 分组任务。

这是任务结构示意，不是两倍周期的结论。M2 与 M4 的指令、padding、供数和重叠成本不同。

源端 Router 可以提前输出关系，但不能只按自己的 owner 完成 M4 分组并清空余数。BS40 的每个 owner 只有 2 或 3 行，BS128 也只有 8 行。余数必须跨 owner 继续积累，到全 batch 结束才能确定尾组。若未来做流式通信，还需要明确每个源的完成标记，不能把“当前暂时无任务”当作结束。

05

第一版 ABI：Router 发布 expert slot mask

待落地设计第一版保留原来的 BF16 hidden、BF16 route weights 和 INT32 expert IDs，附带一段按目的 expert-core 排列的 metadata。现有一次 rank-major AllGather 同时传递这段数据；Routed 只读取自己负责的专家切片。

owner_block =
    hidden_bf16[Q, H]
  + router_weight_bf16[Q, K]
  + router_id_i32[Q, K]
  + route_mask_bf16[Q, EP * cores_per_rank, E_core_aligned]

Current physical layout:
    H = 4096, K = 8, EP = 4, cores_per_rank = 2
    experts_per_EP = 72, E_core = 36, E_core_aligned = 40
    Q = max(owner_token_counts) = ceil(BS / 16)

mask[token, destination, expert_lane]:
    bit k = original TopK slot k selects this physical expert

这里的 EP4 × 72 是当前物理专家布局。目的核有 8 个，每个负责 36 个专家；BF16 一行从 36 项对齐到 40 项，行长 80 bytes。每个 token 的完整 sidecar 是 8 × 40 × 2 = 640 bytes。每个源 token 写自己的完整区域，padding 专家和无效行每轮清零。

TopK 为 8，因此 slot mask 在 0～255 之间，这些整数都能被 BF16 精确表示。这是metadata 编码，不涉及近似概率。先选 BF16，是为了绕开当前 INT32 ID 的逐字节重建及窄整数 layout 风险；UINT8 可以随后做 A/B，不能预先假定物理 DMA 或 SRAM 占用减半。

改 owner stride 会影响所有消费者。即使旧字段在 owner 内的偏移不变，新 owner block 变长后，Shared、Routed、Reduce 的跨 owner 寻址都要更新。transport format、Graph cache key 与各 rank 必须使用一致版本；mHC/Router 融合入口也必须正确生成 sidecar。

接收端从“识别所有关系”变成“消费已有关系”

当前 Routed 在各窗口读取 raw IDs，展开本核 36 个专家与 GROUP_T × 8 路由的比较，再构造 slot mask、bitmap 和 count。新接口让 Router 在已经拥有本地 IDs 的位置生成关系；接收端合并本核切片、提取下一个 M4。TP4 的同组 rank 仍计算各自权重分片，但不必各自重新识别同一套路由。

consumer 仍有真实成本：读取 16 个 owner 切片、构造有界 bitmap、定位有效行、生成 gather 描述符。BS128 的 bitmap 要使用多个精确整数段，例如 16-bit chunks，不能把 128-bit bitset 塞进一个 FP32。第一版不要求全局原子操作或动态 CSR scatter。

  • 沿用原 TopK、校准、logical → physical expert 映射、route weight 的 BF16 舍入；sidecar 依据映射后的物理 expert ID。

  • 通用调度规则：依据 memory effect、alias、依赖和资源可用性移动操作，不允许靠函数名判断是否开启重排。
  • 有限验证探针：先编译 metadata 输出、跨 owner 读取、动态四行 gather，再接完整 Gate/Up/Down。双缓冲编译显式开启，保留自动 PE 配置。

新结构也可能增加 hidden 重读：同一 token 属于多个专家，按需 gather 会重复读 BF16。需要对比“纯按需读”与“小 FP8 cache”。若源端额外发送 FP8 hidden，同时为 Shared 保留 BF16，hidden 部分的载荷会增加约 50%；因此第一版仅改 metadata，不把这项流量变化藏在结果里。

08

先选择最能判断方向的一版

候选能解决什么代价与顺序
只附带 FP32 expert IDs减少 INT32 字节重建仍有 expert × route 比较与窗口限制；作为低改动对照
BF16 expert slot-mask生产端生成关系，消费端全局合组，无需先做动态 CSR scatter增加 7.77% payload 和 Router VP/ST；优先验证
稀疏 CSR / sorted referencesmetadata 更紧凑，直接表达每专家 token 列表prefix-sum、动态 scatter 和发布成本未知；dense sidecar 成本过高时继续推进
独立 receiver 全局 planner现有 Router 改动少容易重复串行 CT/VReg 规划瓶颈；planner、写回、读取与等待全部计费
expert-major hidden / AllToAll提供连续专家输入，更大 BS 的长期方向额外复制、TP/EP 通信拓扑、combine 映射和负载均衡一起变化；需要独立完整设计
只扩大 GROUP_T / 调 allocator改善某些容量临界点全局 hidden cache 仍随 T 增长；可作为配套，不承担架构解耦

这与此前“跨窗口余数队列”的区别，是把路由关系生成移到分布式 Router producer，并提供便于直接读取的格式。若仍让 Routed 串行扫描所有 route、维护 36 个专家状态，再发布任务，结构上虽然省了尾组，也可能被 planning 时间抵消。本轮必须同时证明 relation 生成更便宜、全局合组有效、供数流水能持续。

更大 BS 的下一层：一个权重 tile 能否连续服务多个 M4？

即使消除了窗口，若每个满 M4 都重新遍历权重，随着尾组比例下降，收益也会逐渐饱和。进一步优化可以探索“同专家连续调度 + 权重 tile 驻留”：保持 PE 的 M4 映射，让多个 M4 连续消费同一段权重，而不直接改成 M8。

这取决于 weight memory → WL1 → PE 路径能否显式保留或实际复用该 tile，不能靠共享 descriptor 就假定没有重读。应先用 IR/汇编探针对照权重路径字节与 cycle；若需要交换 M/K 循环次序，还要核算多个 M4 累加器的 SRAM 占用。它是后续硬件可行性研究项，本轮 sidecar 组数结果没有计入这项收益。

09

先过 BS40 不掉速，再追 25% 吞吐

验收比较同一个候选、同一输入分布、同一工具链下的 BS32 与 BS40。硬门槛是：

C40_new ≤ (40 / 32) × C32_new
同时要求 BS32 自身不因改造回退，不能通过放慢 BS32 凑平曲线。

用归档 BS32 作为预算参照，BS40 的 Routed C42 要从 2,457,180.51 降到 ≤ 2,134,616.96，需要约 13.13% cycle 降幅。若新 BS32 也变快，BS40 门槛还要收紧。目标“吞吐 +25%”对应 cycles × 0.8，不是 cycles −25%。

冻结配对基线：BS32 / 40 / 128

最新 kernel 与 compiler、默认 PE 搜索、固定 route / 数值阈值。先记录完整 Routed、Router、通信和整体组件时间，以及 PE gap 分布。

独立验证 Router sidecar 与传输

证明旧 IDs / weights 不变，sidecar 与 padding 正确；分别测新增 VP/ST、真实 AllGather 载荷及延迟。设备生成索引，不能用 host plan 上传替代。

先单槽贯通，再接双槽流水

从完整全局合组 + 单槽 M4 开始；确认输出与 Reduce 语义后，叠加 next-task、metadata load 和四行 gather。检查 IR / 汇编的地址复用、DT、同步和 drain。

针对主导瓶颈做 A/B

按需 BF16 gather 对小 FP8 cache；批量描述符对旧读取；通用 live-range / 调度优化对原分配。每个变量分别衡量，记录 LD 重读与等待来源。

扩大曲线与真实路由覆盖

BS40 过线后，扩到 15 档 BS 和原 49 个采样点；关键 shape 做 VCS/RTL，检查 changed-input Graph。BS>128 再测 metadata tile、尾组与通信扩展。

正确性和 cycle 分开测，planning 必须入账

正确性进程覆盖 full / tail、重复 expert、无效 ID、空 owner、跨边界、不同 rank/core 与 replay 状态变化；cycle 进程单独运行。必须报告旧阶段和新阶段的完整边界，不能只展示删掉 planner 后的 PE executor。

Per-layer measurement, respecting actual dependencies:
    max_owner(Router + metadata emission)
  + collective
  + max_rank(Shared + Routed + Reduce)

Also report:
    Routed cycles, planning cycles, PE busy / gaps,
    activation LD bytes, weight-path bytes, DT / ST,
    peak-live SRAM, output equivalence and replay coverage.

有通信计算重叠时，使用实际依赖时间线核算，不能把已重叠时间重复相加。该组件边界仍不等于含 H1 / host 的服务端端到端吞吐。Routed +25% 也不自动等于整体 MoE +25%。
