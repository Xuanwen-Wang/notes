01 / DATA OWNERSHIP

所有设备算出的部分结果，怎样合成同一份答案？

假设两个 rank 分别持有同样形状的张量：rank 0 是 [1, 2]，rank 1 是 [10, 20]。对它们做求和型 AllReduce，最后两个 rank 都得到 [11, 22]。参与者原来各有一份输入，结束时各有一份完整的归约结果。

每个 rank 的输出：Y = X0 + X1 + … + XP−1

AllReduce 同时包含“合并”和“让所有参与者拿到结果”。在张量并行里，不同设备算出了一个矩阵乘的不同部分，可能需要把部分输出相加；在数据并行训练里，参与者可能需要汇总梯度。通信库负责协调这些张量的移动、归约和完成顺序。

ZCCL 的全称是 Zeus Collective Communications Library。它面向 Zeus NPU，API 形状借鉴 NCCL。实现主要分为 C++ 的通信器、拓扑和调度，以及设备上的搬运、归约 kernel。本文从默认的 SUM、FP32/BF16 路径往下追。S1

操作结束后的结果放在哪里与 AllReduce 的关系
Reduce某一个指定参与者得到归约结果只完成归约，未让所有参与者拿到结果
ReduceScatter结果按块分散，每个 rank 拿一块先把每块结果算完整，再把不同块交给不同 owner
AllGather各 rank 的块被收集成完整张量，每个 rank 都有一份把 ReduceScatter 的分散结果拼回去
AllReduce每个 rank 都拿到完整归约张量本版的两类算法都可以按 ReduceScatter → AllGather 理解
此表解释操作语义。它不表示本版 ZCCL 已经原生实现表中所有 API。

把一整个张量送给某张卡、由它包办求和再发回，在语义上可以完成 AllReduce。但这个中心会承担大量流量和串行工作。ZCCL 采用分块、分散归约和协同分发，让设备与链路一起工作。下面先看它们能够通过哪些链路合作。

02 / NAMES BEFORE WIRES

rank、device、core、board 是四个不同的概念

名称在本文中的含义需要记住的区别
rank一个通信组中的逻辑编号，范围为 0 到 P−1换一个子通信组，编号可能重排
device运行时可选择、可绑定的 Zeus 设备设备 ID 与通信组 rank 之间有显式映射
core同一 device 内执行 kernel 的计算核心PS1 仿真配置中，每个 device 有 2 个 core
board当前拓扑模型中连续 4 个 device 形成的分组这里是源码中的 board 分组；真实板卡、封装、die 数量需要板级资料确认

当前框架的主线是一进程绑定一个 device，进程组里的 rank 通过通信器关联到实际 device。一个 device 有两个 core，并不会使通信组的 world size 自动翻倍。16 个 rank 各绑定一个双核 device，仍然是 world size 16，设备内部则一共有 32 个 core。S2S5

下面的 16 路示例采用最直观的映射：rank r 绑定 device Dr。实际子组不必如此。例如，一个子组的 rank 0 可以绑定 D4。ZCCL 初始化时会收集这张映射表，再把物理邻接关系投影进通信组。S4

通信组回答“谁参与这次运算”，物理拓扑回答“谁能直接访问谁”。两张表要对齐，才能得到可执行的通信计划。
03 / THE PS1 FABRIC

板内全互联，板间沿环连接

在当前 16-device PS1 模型中，D0–D3、D4–D7、D8–D11、D12–D15 分成四个 board。每个 device 有四个逻辑 PBLink 端口：三个连接本 board 的其他三个 device，一个连接相邻 board 上的特定 device。S5

具体到 D0，它的直连邻居是 D1、D2、D3、D14。D4 虽然也是同一台系统里的设备，但本版 transport 不为 D0→D4 建立直接连接。某个分块可以经由 D0→D2→D4 这样的路径流转，其中 D2 上的 kernel 负责接收和转发。

这解释了一个容易混淆的地方：图上存在多跳路径，不等于一个 peer 指针能够自动访问任意远端 device。ZCCL 当前只为直连 PBLink 邻居建立连接；更远的流转由通信算法安排中间设备完成。拓扑代价计算也限定在 PBLink 图上，没有借 CPU、PCIe 或 NIC 节点偷偷补一条 tensor 数据路径。S12S5

源码允许用 ZCCL_TOPO_FILE 提供 XML 拓扑。没有合适的 XML 时，会按 board/local 规则构造软件拓扑。本次把 ZCCL 的邻居集合与 torch_zeus 的 PS1 JSON 逐设备对照，16 个 device 的邻居集合一致；这个核对没有把每个端口编号或实板引脚当作已验证事实。

证据口径：本节讲的是 ZCCL 和仿真运行时共同采用的软件互联模型。真实板级连线、封装方式、链路单双向速率和竞争行为，不从这些分组名称直接推断。

05 / FROM PYTORCH TO THE C API

一次 dist.all_reduce，实际经过哪些函数？

应用通常从类似下面的调用开始。参与同一通信组的进程应提交匹配的张量形状、dtype、操作和调用顺序；否则对端可能永远等不到对应消息。

# Each process owns a Zeus tensor x in the same process group.
dist.all_reduce(x, op=dist.ReduceOp.SUM, group=group)

# Asynchronous submission returns a Work handle.
work = dist.all_reduce(x, op=dist.ReduceOp.SUM,
                       group=group, async_op=True)
work.wait()
  1. ProcessGroupZCCL::allreduce()

    检查单设备张量，把输入、输出、元素数、dtype、reduce op 和 stream 传入公共 collective 路径。

  2. ProcessGroupZCCL::collective()

    准备或复用通信器，选择执行 stream，保留必要的张量生命周期，提交实际操作并记录完成 event。

  3. zcclAllReduce(sendbuff, recvbuff, count, dtype, op, comm, stream)

    C API 把参数包装为 zcclInfo，交给统一调度入口。

  4. zcclEnqueueCheck() → setupCollKernel()

    检查参数与 stream，选择专用算法或 Ring，把工作项放入通信器队列。

  5. launchKernel() → launchCustom() / launchRingElem()

    整理 kernel 参数，选择已经编译好的 zbin，通过 zeusLaunchKernel 下发。

  6. Triton kernel → load / store / reduce / poll

    设备核访问本地和映射的对端缓冲区，完成 PBLink 搬运、归约与计数器握手。

PyTorch 的这个 AllReduce 使用 原地结果：collective(tensors, tensors, …)，因此最终答案覆盖原 tensor。ZCCL 的 C API 本身同时接收输入与输出指针，能够表示更一般的调用。S2S3S6

到这里 CPU 做的是检查、选择、排队和提交。张量里的每个数字如何跨设备移动，要继续看通信器建立出的 peer 地址，以及设备 kernel 的读写。

06 / CONTROL PLANE AND MEMORY MAPPINGS

第一次调用之前，先让参与者认识彼此

通信器可以理解为一个已经准备好的通信小组：谁是成员、每个成员绑定哪个设备、能访问哪些邻居、缓冲区在哪里、该使用什么算法。第一次调用需要准备这些状态；后续调用通常复用缓存的通信器。S4

  1. 生成和分发唯一 ID。通信组根 rank 生成 ZCCL unique ID，通过 PyTorch 的 Store 交给其他 rank。这是在帮助进程进入同一个小组。
  2. 绑定 device，建立 bootstrap 通道。zcclCommInitRank 绑定调用线程当前选择的设备。ZCCL 的 bootstrap 使用 Unix Domain Socket 做节点内进程间 rendezvous 和控制消息交换。
  3. 收集 rank→device 映射。每个 rank 提供自己绑定的 device ID，所有 rank 得到同一份成员表，并核对看到的拓扑一致。
  4. 建立拓扑、寻找 Ring。读取 XML 或构造 board fabric，计算 PBLink 路径代价，并生成逻辑 ring 的 prev / next。
  5. 为全部直连邻居建立 FIFO。连接范围覆盖所有直连端口，使专用算法可以在不同阶段使用不同邻居。
  6. 交换 IPC 内存句柄并映射。每个 rank 分配自己拥有的控制块和接收区，发送可导入的句柄，对端调用 zeusIpcOpenMemHandle 得到可访问的映射地址。
  7. 准备兼容的专用算法。检查程序需要的每条链路是否真的存在，准备可复用的 kernel、scratch 与设备侧状态。
控制面 / CPU

unique ID、rank/device 列表、拓扑指纹、IPC handle、连接状态。

通过 Store 与 bootstrap 交换。handle 是描述一段内存如何被导入的信息，不是把整个 tensor 装进控制消息。

数据面 / NPU + PBLink

tensor 分块、归约中间结果、FIFO payload，以及通知数据就绪或槽位空闲的计数器。

由设备 kernel 访问映射的内存，并按协议推进。

peer 指针也不能凭空填一个“看起来像对端地址”的数字。本版 transport 要求真实 IPC 导入成功；映射失败就会使连接建立失败。仿真运行时还检查 owner device 与 importer device 的 peer 可达性。S12S16

这套控制面只在初始化和必要的准备阶段交换元信息。稳定运行的 AllReduce 批量数据经由设备 kernel 和 PBLink 流动；当前 ZCCL 尚未实现跨节点 IB / RoCE / TCP 数据 transport。初始化里出现 socket，并不能据此推断 tensor 走了网络。

07 / ALGORITHM SELECTION

同一个 AllReduce API，下面可能走两类 kernel

setupCollKernel() 按顺序做选择。以下是本文求和型 AllReduce 的主要分支；直接 symmetric-window AllGather 是另一个操作的快速路径，不在本次 AllReduce 主线里。S6

顺序条件路径
1通信组只有一个 rank局部处理，无需跨设备交换；框架层也有相应短路
2已准备的专用算法匹配拓扑、dtype、op，且有对应专用 kernellaunchCustom：优先使用完整 board 的 n4 或兼容 PS1 的 n16 调度
3专用算法未覆盖，但 Ring kernel 覆盖此组合launchRingElem：按 prev / next 传递分块
4两类 kernel 都不覆盖返回 zcclInvalidUsage，不把不支持的组合当作成功

本版普通归约调用自动注册的专用程序包括 Allreduce.n4-PS1Board-rs1-ag1-steps2 和 Allreduce.n16-PS1-rs4-ag4。n4 必须对应完整、可匹配的 board。例如 D4–D7 也能作为一个完整 board 使用 n4；跨 board 的四设备子组则要看实际连线，不能只因 nranks == 4 就套上同一程序。S7

普通 AllReduce 自动选择专用路径时，还要求已经有该程序、dtype 和 rank 的专门编译版本。可解释执行任意 ZE 程序的 interpreter 主要服务显式 handle API；本版没有把它作为普通 AllReduce 的默认兜底。S7

因此，想确认某次调用真正跑了什么，要同时知道：通信组绑定的设备集合、dtype/op、选择到的 kernel、消息大小。仅从 API 名字无法区分 n4、n16 和 Ring。

08 / BUILD TIME VERSUS RUN TIME

Triton 源码在构建时变成 zbin

当前这条 ZCCL 交付路径使用提前编译的设备 kernel。构建 ZCCL 时，zecc 把 Triton 源码编成包含 .zbin 数据符号的目标文件，随后链接进 libzccl.so / libzccl_static.a。运行 AllReduce 时，ZCCL 选取这些符号所指向的 kernel，再调用运行时发射。S8

构建阶段

  1. algorithms/ps1/*.ze.json

    每个 device、每个 core 的 send / recv / reduce / sync 顺序。

  2. generate_custom_specialized_triton.py

    按 program、dtype、rank、大小块 variant 生成完全展开的 Triton 代码。

  3. zecc → zeus-compiler → .zbin

    编译设备代码，封装为带数据符号的目标文件。

  4. libzccl.so

    链接主机调度代码和设备 kernel 数据。

运行阶段

  1. setupCollKernel()

    从已经具备的程序中选择适合当前通信组的一个。

  2. launchCustomRaw()

    选本 rank 的 kernel，准备输入、输出、count、scratch 和 peer FIFO 参数。

  3. zeusLaunchKernel(zbin, cores, args, stream)

    在指定 stream 上提交，专用程序使用两个 core。

  4. core = tl.program_id(0)

    core0 与 core1 执行各自静态展开的操作序列。

两类源码很值得对照：Ring 的主体在 src/zccl/device/triton/zccl_ring_collectives.py；PS1 专用算法的主体则由 JSON 和生成器共同决定，生成的每个 rank 的 .py 位于构建目录。只盯着固定的 zccl_allreduce_ring_f32.py，会漏掉普通 n4/n16 调用优先选择的专用 kernel。

主机传给 kernel 的是扁平参数表：输入、输出、count、scratch，以及各出入连接的 head / tail / payload 指针。专用 FIFO ABI 是 28 个参数，Ring ABI 是 14 个参数。当前源码把这些地址在主机端准备好，kernel 无需重新做拓扑发现。S7

专用 Triton kernel 还有一般块与小块版本。单个 chunk 不超过 16 KiB 时，可选择直线的小块版本；更大时进入分块循环。这个选择取决于 chunk 大小，不是只看整 tensor 大小。

09 / THE FOUR-DEVICE BOARD

4 路专用算法：每个 rank 负责算完整的一块

把每个输入张量分成 C0、C1、C2、C3 四块。先让 D0 收齐四个输入中的 C0，D1 收齐四份 C1，依此类推；每个 owner 把自己的块求和。ReduceScatter 结束后，四个不同的完整结果分别属于四个 rank。接着做 AllGather，每个 owner 把完整结果分发给其他 rank。

教学整数示例。后续阶段只显示完整归约结果的归属，不表示所有中间缓冲区的逐字节快照。

board 内四个 device 两两直连，因此 owner 可以从另外三个 device 直接取得对应 chunk。本版 n4 程序被命名为 rs1-ag1-steps2：一个逻辑 ReduceScatter 阶段，加一个逻辑 AllGather 阶段。每个阶段仍然包含多次 DMA、计数器访问和局部计算，不能把“一个阶段”读成“一个硬件周期”。S9

源码中 D0 的两核分工非常具体：

D0 的执行者ReduceScatter 阶段两核会合后
core0准备自己的部分输入；发送 C2；从 D1、D2、D3 接收并累加 C0把完整 C0 发送给 D1、D3，并接收完整 C2
core1准备另外的部分输入；发送 C1 给 D1，发送 C3 给 D3把完整 C0 发送给 D2，并接收完整 C1、C3

C0 是 core0 算完的，但发给 D2 的任务在 core1 上。所以中间的 tl.zeus.barrier() 保证 core1 发出的是已经归约完成的结果。这是同一 device 内的两核交接，与两张设备之间的 FIFO 握手属于不同层。生成器还会转发或消除部分不必要的本地 copy，因此上表是在解释原始 ZE 程序的数据依赖，不要求生成代码逐条保留所有 copy。S15

10 / A REAL CHUNK IN THE N16 PROGRAM

16 路的 C0，怎样沿着板内和板间连线汇聚？

16 路程序把每个输入切成 16 块。C0 只是其中一块，其余 C1–C15 也在执行各自的路线。本文单独抽出 C0，才能看清每份输入的来源和中转，而不被所有并行传输淹没。

下面的步骤直接来自 Allreduce.n16-PS1-rs4-ag4.ze.json。其中的 alg_step 是静态计划的阶段标记。不同设备之间没有一个为每步敲钟的全局控制器；接收方等到实际数据就绪才继续。S10

阶段C0 的实际流转贡献怎样合并
RS · 0D8、D9、D10 → D11D11 加上自身贡献，持有 Board 2 的 4 份
RS · 1D5、D6、D7 → D4；D11 → D13D4 得到 Board 1 的 4 份；D13 汇入 D11 的 4 份，加上自身成为 5 份
RS · 2D4 → D2；D12、D13、D15 → D14D2 得到自身 + Board 1，共 5 份；D14 得到 Board 2 + Board 3，共 8 份
RS · 3D1、D2、D3、D14 → D0D0：自身 1 + D1 的 1 + D2 的 5 + D3 的 1 + D14 的 8 = 16 份
AG · 4D0 → D1、D2、D3、D14完整 C0 开始扩散，接收的是完整答案，不再继续归约
AG · 5D2 → D4；D14 → D12、D13、D15完整 C0 进入 Board 1，并扩散到 Board 3
AG · 6D4 → D5、D6、D7；D13 → D11Board 1 全部拿到答案，完整 C0 回到 Board 2
AG · 7D11 → D8、D9、D10全部 16 个 device 都持有完整 C0

这里可以同时看到三件事：板内先合并一部分贡献；板间只走真实的直接邻居；中间 device 在转发前可以加入自己的贡献。PBLink 搬运字节，归约加法由设备 kernel 执行。D14→D0 是模型中的直接板间连接，图上绕到左侧画出，是为了避免误看成经过 D12 或 D2 的多跳路径。

本次还对整个 n16 JSON 做了静态符号推演：把 rank r 的输入标记为集合 {r}，按每个 core 的操作顺序执行 copy、FIFO send/recv、集合并和本地 barrier。检查了 16 rank × 16 个输出 chunk：每个输出都包含 0–15 的贡献各一次，消息地址匹配，符号调度能够完成。

这个检查验证了原始算法计划的贡献覆盖与 FIFO 匹配。它没有执行浮点运算，没有经过 Triton lowering，也没有验证 DMA 时序、硬件可见性或实板带宽；不能替代 kernel 仿真与硬件测试。

11 / THE RING FALLBACK

没有合适的专用程序时，让部分和沿环流动

Ring 的逻辑是给每个 rank 指定一个前驱 prev 和一个后继 next。发送只去 next，接收只从 prev 来。环是通信算法在拓扑上选出的顺序；每条环边仍然需要实际可用的直接连接。S11

# Logical Ring AllReduce structure, simplified from the source.
chunk = ceil_div(count, world)
my_chunk = recv + rank * chunk

counters = reduce_scatter_ring(
    send, my_chunk, scratch, chunk, count, peer_fifos)
all_gather_ring(
    my_chunk, recv, chunk, count, peer_fifos,
    counter_state=counters)

ReduceScatter：某个 owner 的 chunk 作为一个“部分和 token”沿环前进。每个经过的 rank 接收前面的部分和，加上自己对同一 chunk 的贡献，再发给 next；最后在该 chunk 的 owner 上落地。所有 chunk 交错执行同样的逻辑。

AllGather：完整结果已经算好。现在每个 rank 把自己拿到的结果块发给 next，同时从 prev 接收另外一块。收到的完整块可以继续转发，经过 P−1 次邻居交换后，各 rank 取得所有块。

源码特别把 ReduceScatter 的 FIFO 计数器状态继续传给 AllGather。两阶段衔接时没有把计数器随意清零；通信器上的协议状态保持连贯。大 chunk 会切成不超过一个 FIFO 槽位的 piece，避免所有 rank 把整块全部塞进有限队列后一起堵住。S11

本版 Ring 的 launch 使用一个 core；n4/n16 专用程序使用两个 core，并可在计划中切换不同端口。专用程序依赖特定拓扑，Ring 是覆盖其他兼容组合的基础路径。选择哪个更快，还取决于消息大小、端口竞争和实现代价，不能只按“阶段更少”计算加速倍数。

当 count 不能整除 world 时，两条路径处理方式不同：Ring 按向上取整的 stride 计算每块实际长度并裁短尾块；专用 ZE 计划使用固定完整 chunk，因此先补零到 world × chunk，运行后只拷回有效元素。求和时补零不增加贡献。S20

12 / BYTES ACROSS PBLINK

一条 A→B 的传输，数据和计数器分别在哪？

一个方向的连接包含一组有界 FIFO。它把数据区放在接收方，把消费确认放在发送方。A 和 B 各自持有本地地址，也通过 IPC 映射取得需要远程访问的那部分地址。S12S13

A 的本地设备内存

SendMem.head

表示 B 已经消费到哪里。

B 更新这个计数器，A 读取它判断是否有空间继续发送。

内存归 A 所有，但写这个计数器的参与者是 B。

B 的本地设备内存

RecvMem.tail + payload

tail 表示 A 已经发布了多少消息，payload 保存实际数据。

A 写入这两部分，B 读取 tail 并消费 payload。

内存归 B 所有，数据由 A 经映射写入。

A ── payload / tail ──▶ B
A ◀──── head ───────── B
参数当前 ABI意义
槽位数8同一方向上可承载有限数量的在途消息
每槽容量64 KiB一个 piece 的 payload 上限
payload 总容量512 KiB / 邻居 / 接收方向有界工作缓冲，不需要为整个大 tensor 预留同样大的通信队列
计数器自由递增的 uint32 head / tail使用差值判断空满，使用 counter & 7 选物理槽位
对齐计数器位于各自 4 KiB 对齐块的首地址；payload 跨过接收头部满足当前设备 kernel 指针参数的页地址 ABI

发送方遵守的协议是：先等到有空槽，再写 payload，最后发布 tail。接收方遵守的协议是：先等到 tail 表示消息就绪，再读取或归约 payload，消费结束后归还 head。

# Protocol sketch. Actual kernels use tracked counters and tiled DMA.
# Sender A:
wait_until(tail - head < 8)
slot = tail & 7
copy(local_chunk, peer_B.payload[slot])
publish(peer_B.tail, tail + 1)

# Receiver B:
wait_until(tail - head > 0)
slot = head & 7
consume_or_reduce(local_payload[slot])
publish(peer_A.head, head + 1)

tail 解决“数据有没有到”的问题；head 解决“发送方可不可以覆盖旧数据”的问题。如果只通知新数据、没有消费确认，FIFO 绕一圈后就可能覆盖接收方还没读完的数据。这就是软件协议的 credit / 背压。

这层 8-slot credit 是 ZCCL 的软件流控。PBLink 物理链路内部可能还有自己的缓冲、报文和硬件流控，不能把这里的 8 个槽位当成 PHY 层的全部能力。

13 / INSIDE THE DEVICE KERNEL

跨设备“发送”，落实为一次远端映射上的 store

发送方 kernel 已经拿到对端 FIFO payload 的映射指针。主路径里的 zccl_move() 用 block pointer 读取本地数据，再把数据写到映射的目标区。接收方随后读取自己本地的 payload；需要归约时，再读自己的累加值，执行加法并保存。S14

# Simplified one-block form of zccl_move.
values = tl.load(src_block, boundary_check=(0,), padding_option="zero")
if reduce:
    old = tl.load(acc_block, boundary_check=(0,), padding_option="zero")
    values = (values + old).to(values.dtype)
tl.store(dst_block, values, boundary_check=(0,))

这里的 src_block / dst_block 是根据本次操作绑定的：发送时通常是“本地输入或部分和 → 对端 payload”；接收时通常是“本地 payload → 本地输出或 scratch”。具体访问哪块设备内存，取决于 host 准备的映射地址。同一套 Triton 读写语义因此能够承载本地计算和跨 PBLink 的访问。

从执行模型看，数据会经过设备的搬运与片上工作存储，再由 Zeus 指令执行 load、store 和向量归约。CCL 代码描述的是这些动作的顺序；真正的远端地址窗口、链路报文与物理传输由运行时和设备互联实现承接。当前源码中的 real-runtime 分支委托给厂商 zeusIpcOpenMemHandle，仿真分支则检查拓扑并打开仿真的 IPC 映射。S16

chunk按 owner 划分归约结果16 路时每块 1 MiB

一般块路径把两个 DMA block 成对组织，归约时还读取两个累加 block；尾部不足时按边界处理。小块版本可以直接执行一个 block。消息大于 64 KiB 并不意味着 AllReduce 不支持：kernel 会按 piece 循环复用 FIFO，而不是把整个 chunk 一次性塞进队列。

专用生成器还会把自己拥有的计数器状态保存在寄存器中，减少反复加载；tail 仍要按协议发布，让对端知道新数据。head 则在其他 core、后续 launch 或 credit 等待方需要观察时发布。内存读取次数被减少了，数据就绪和槽位归还的协议仍然保留。

14 / THREE DISTINCT SYNCHRONIZATION SCOPES

同步不只有一种，三层分别守住三种依赖

层次要保证的事情当前机制
同一进程内，计算与通信之间输入先算完，通信才能读；输出通信结束后，后续计算才能用stream 顺序、event 记录与等待、Work 完成状态
同一 device 的两个 core 之间一个 core 的中间结果准备好后，另一个 core 才能读取或发送专用 kernel 的 tl.zeus.barrier()；interpreter 的 epoch 计数握手
两个 device 之间payload 就绪后才消费，消费后才覆盖对应槽位FIFO tail / head 与 volatile 轮询

计算 stream 与通信 stream 的交接

本版框架中，普通同步调用使用调用者当前 stream；异步调用或合并提交可使用专用通信 stream。切到通信 stream 时，先在生产输入的 stream 上记录 event，再让通信 stream 等它，确保此前计算已经完成。通信结束 event 则用于把后续工作排在通信之后。S3

work.wait() 首先建立当前 stream 对通信完成的依赖。默认语义不要求 CPU 一直忙等到硬件结束；显式超时、blocking-wait 等模式会进一步触发主机侧等待。API 已返回、kernel 已提交、设备已完成，是三个需要区分的时点。S16

本地两核的交接

静态生成的专用程序可以在已知的位置插入 tl.zeus.barrier()。生成器的执行约定是先排空该核相关的在途 DMA，再完成两核会合。对解释器中的动态操作序列，则用两个 core 分别推进自己的 epoch，并轮询对方 epoch 来交接。n4 中“core0 算 C0、core1 发给 D2”就是必须建立这种依赖的具体例子。S15

跨设备的就绪与确认

等待 tail/head 的循环使用 tl.load(..., volatile=True)，让编译器持续重读那个会被对端修改的值。否则一次读数若被提升到循环外，kernel 就可能一直盯着旧值。volatile 在这里首先解决“重新读取”问题，不能单凭这个关键字推导任意硬件上的完整 acquire/release 语义。

协议要求 payload 的发布先于 tail 被接收方视为就绪，消费完成先于 head 被发送方视为可复用。源码按这个协议组织操作，编译后的设备指令与硬件可见性规则需要落实它。项目文档记录了普通 store 发布计数器的仿真结果；这篇教程没有把这些记录扩大成对全部硅片内存顺序的独立认证。S14S15

zcclGroupStart / zcclGroupEnd 主要组织主机侧分组提交与延后 launch。它们不会自动替代本地 core barrier，也不会替代跨设备的 FIFO 数据握手。
15 / ONE INVOCATION, IN ORDER

从前一个算子，到后一个算子

把前面的层次合起来，一次稳定态的异步 AllReduce 可以按下面的顺序理解。下图只表示先后依赖，不按实际耗时比例绘制。

计算输入 X→记录 ready

等待 ready→AllReduce kernel→记录 done

  1. 当前设备已经绑定，通信器与 peer 连接可复用；首次调用额外承担初始化工作。
  2. 框架检查输入并选择 stream，处理张量在异步执行期间的生命周期。
  3. ZCCL 把 AllReduce 变成一个专用或 Ring 工作项。
  4. 运行时提交本设备的 kernel。所有参与 rank 都要提交对应工作，彼此才能持续获得消息。
  5. 两个 core 按本地计划工作，设备间经 FIFO 完成 send、recv、reduce；需要的中间结果通过相应层次的同步保护。
  6. 本设备的 kernel 完成后，通信 stream 的完成 event 推进。消费者在对应依赖满足后读取结果。

Graph capture / replay 怎样接进来？

本版 ProcessGroupZCCL::collective() 要求通信器及匹配操作签名的准备工作先在 eager 阶段完成。进入 capture 后，collective 在捕获 stream 上运行，保留相关资源，后续 replay 才能重现设备操作与 stream 顺序。不能在 capture 中临时重新建组。S3

库层测试与框架层接口还要分开看：ZCCL 自己的测试覆盖了若干 capture/replay 场景；本文读取的 torch_zeus 版本中，ProcessGroupZCCL::barrier() 仍明确拒绝在 Graph capture 中调用。支持某些 AllReduce capture 场景，不表示每个分布式 API 都可被捕获。S17

16 / READING THE COST

延迟取决于搬多少、走哪里、等什么

理解这些机制后，通信性能就可以拆成几个具体问题：每条链路搬了多少字节？能同时使用哪些端口？一次 kernel 发射与小计数器访问有多贵？某个 rank 是否因为输入较晚或路径竞争，让其他设备一直等待？

场景值得先看的因素从源码能推到哪里
小 tensor提交、轮询、barrier、地址准备、小块直线 kernel能识别固定开销来源；不能仅从代码行数给出实测微秒数
大 tensor数据量、链路争用、piece 循环、DMA 组织、可同时使用的端口能建立流量模型；持续有效带宽仍需测量
完整 board 的 n4三邻居直接交换与双核工作分配无需让某个 chunk 沿一个长环绕行才能收齐板内贡献
完整 PS1 的 n16板内归约、板间汇聚、中间设备转发和反向分发逻辑调度是 4 个 RS alg_step + 4 个 AG alg_step
部分通信组rank→device 映射、直连边是否存在、选路是否落到 Ring通信组大小相同，不代表拓扑和执行路径相同

在均匀分块、忽略协议控制消息的理想 Ring 模型里，大小为 S 的 AllReduce，每 rank 的发送总量约为 2 × (P−1) / P × S：ReduceScatter 和 AllGather 各发送 P−1 个大小约为 S/P 的块。这个公式描述 payload 流量，不直接给出延迟；它也不能原封不动代替特定 PS1 专用程序在每条物理边上的流量。S11

拓扑源码给 PBLink 设置了 16.0 × 0.6 = 9.6 GB/s 的有效带宽参数，用于图的成本表达。这是当前软件模型的参数，不是本文测得的单链路有效带宽。链路方向口径、竞争、DMA 开销、运行频率及运行时行为都可能影响实际结果。S18

同样，n16 的“4+4 个阶段”与 Ring 的邻居迭代数，不能直接相除当成加速倍数。一个阶段里可能有多个发送、接收、计算与等待；真实耗时要看关键路径和并发资源。JSON 中的 costs、makespan 也属于算法模型，不能直接读成已经测得的 hardware cycles。

kernel 计算时间、集合通信时间、通信与计算的重叠、整层耗时，是不同的统计范围。分析完整模型时要沿着同一输入与执行范围计时，不能把局部 kernel 或通信阶段的百分比直接当成整模型收益。

18 / CHECK YOUR MENTAL MODEL

能回答这些问题，就已经抓住主线了

D0 和 D4 都在同一个 16 路通信组，D0 就能直接写 D4 的 FIFO 吗？

在本文的软件拓扑与本版 transport 中，没有这条直接连接。D0 的直连邻居是 D1、D2、D3、D14；可以由算法安排经 D2 等中间设备流转。通信组成员关系不自动创造物理直连边。

为什么 tail 放在接收方，head 却放在发送方？

接收方需要就近轮询数据是否就绪；发送方需要就近判断空间是否已归还。对端通过映射写计数器，等待的一方在自己的设备内存读取。内存的所有者与计数器的写入者不是同一概念。

64 KiB 的 FIFO 槽位能处理几十 MiB 的 tensor 吗？

可以通过分块循环处理。整 tensor 先按 owner 切成 chunk，每个 chunk 再切成不超过槽位的 piece；每段经过发送、消费和确认后，槽位被复用。

PBLink 在哪里执行加法？

本文这条实现由设备 kernel 读取接收到的 payload 与本地累加值并做加法；PBLink 承担远端内存访问与字节传输。不能把集合通信的“归约”理解成链路自动替 kernel 完成。

每次 all_reduce 都要再跑一次 Python 和 zecc 吗？

本版 ZCCL 这条交付路径在构建时生成并编译设备 kernel，链接进库。运行时选择已有 zbin 并准备参数。其他使用 zecc 的 JIT 场景，需要另外分析。

有了两核 barrier，为什么还需要 FIFO 的 tail/head？

barrier 让同一 device 的两个 core 正确交接；tail/head 让不同 device 的 producer 与 consumer 知道数据和槽位的状态。它们保护的参与者与内存范围不同。

Work 已经返回，后一个算子就可以在任意 stream 使用结果吗？

后一个算子必须建立对通信完成的依赖。框架利用 stream/event 和 Work 同步完成这件事；CPU 返回、设备提交、设备执行完成不是同一个时刻。

S10 · n16 的 C0 路线与静态符号检查
zeus-ccl @ 09bf6d75dcf7 · algorithms/ps1/Allreduce.n16-PS1-rs4-ag4.ze.json

提取所有 addr == 0 的 send / recv / reduce，再以 alg_step 分组，得到正文 8 阶段表。静态执行时为每个 core 保留程序计数器，为每个有向邻居对保留 FIFO；recv 需等对应消息，sync 需等本 device 另一 core。reduce 时检查贡献集合不重叠，最后检查所有输出均为全部 rank 集合。

INPUT[r][chunk] = {r}
SEND:   FIFO[src, dst].push((chunk, contribution_set))
RECV:   wait for FIFO message; verify chunk address
REDUCE: verify disjoint contribution sets, then union
SYNC:   wait for the peer core of the same device

CHECK:  for every r and chunk,
        OUTPUT[r][chunk] == {0, 1, ..., 15}

本次 16×16 输出检查通过。该结果不包含浮点、编译器或硬件执行证据。
