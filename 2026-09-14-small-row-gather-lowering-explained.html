先看原始 kernel：按行号取四行，flag 决定这一行要不要取

这是从 issue #153 抽出的最小 Triton pattern：从 BF16 源矩阵中按运行时行号取数据，写到一个 4 × 128 的输出块。没有 PE 计算，便于单独观察 gather 的下降开销。

Triton 输入代码 · 优化前后写法相同

# Single block, full columns: K = 128
rows = tl.arange(0, 4)
cols = tl.arange(0, 128)
ids = tl.load(row_ids_ptr + rows)
flags = tl.load(flags_ptr + rows)

tile = tl.load(
    src + ids[:, None] * K + cols[None, :],
    mask=(flags[:, None] != 0),
    other=0,
)
tl.store(
    dst + rows[:, None] * 128 + cols[None, :],
    tile,
)

为说明主路径，这里只展示单 block、完整列的核心代码，省略 JIT 包装。实际测试 kernel 还保留运行时 K、k_offset、列边界保护和多 block 路径。

把变量对到实际数据

src：16 × 128 源矩阵；row_ids：4 个源行号；flags：4 个有效性标记；dst：4 × 128 输出。每行 128 个 BF16，连续 256 B。

示意：ids = [7, 2, 7, 10]，flags = [1, 1, 0, 1]。这组值用于解释语义，不是性能验收输入；性能图中四行 flag 都为真。

输出行来源 / 结果
① dst[0, :]取 src[7, :]，搬 256 B
② dst[1, :]取 src[2, :]，搬 256 B
③ dst[2, :]flag 为 0，不读源数据，输出全 0
④ dst[3, :]取 src[10, :]，搬 256 B

ids[:, None] 给每行一个源行号，cols[None, :] 给这一行的 128 个连续列位置；二者组成 4 × 128 的地址块。flag 沿列广播，控制整行是否读取；other=0 保证未读取的位置为 0。

编译时知道“要处理四行”，不知道“取哪四行、哪些行有效”。这就是静态小行数、非末维 gather、末维连续 payload：在行维选数据，每行内部连续。下面比较的是同一段 Triton 被编译器生成了什么代码；临时 mask_tmp 和两个行循环都是下降后的产物。

同一段 Triton，编译器为什么多做了一圈？

先认清谁在做事：CT（控制核）读行号、判断 flag、计算地址；LD 按配置把源数据搬到 L2 中的 result；最后 ST 把 result 写到输出 dst。因此“四条数据 LD”之外，还存在一段 CT 控制工作。

先看下降后的两条路径。左边先把四个 flag 的比较结果写进 L2 临时 buffer，再逐行读回；右边直接用 flag 控制搬运。下面是依据真实 ZeusHigh IR 简化的伪代码，省略地址配置、mail、列 tail 和资源释放。

Before · 两个循环

ids, flags = load_metadata()

mask_tmp = alloc(4 × int32)
for r in range(4):
    mask_tmp[r] = int(flags[r] != 0)

fill_zero(result)
for r in range(4):
    if mask_tmp[r] != 0:
        load_row(r)  # ① ② ③ ④

ids, flags = load_metadata()

# 整个 mask_tmp 生成循环消失

为什么值得尝试？①写 result[0]，②写 result[1]，目标区间互不重叠；源行即使相同也只是重复读。②的行号来自独立的元数据，不是①搬回的数据，所以数据语义没有要求“①搬完才读②行号”。

9 月 14 日已查明：这次等待保护的是开头的 ids 元数据，不是①搬回的数据。InjectSync 把“元数据 DMA → if 内读取 ids”的发送 / 接收放到各 if 入口。到了②的分支，新的 LD_MAIL 已排在①之后；它必须等 LD 队列前面的任务完成，于是本来只想确认 ids 已就绪，却把①的数据搬运也等进来了。

真正需要：ids DMA 完成 → 后续各行可读 ids
当前排布：①数据 LD → LD_MAIL → CT_MAIL → 读 ids[1] → 算②地址 → ②数据 LD
原型排布：先读取 ids[0..3] → 发① → 准备并发②（①仍在搬）→ ③ → ④

纠正前一版的疑点：同步报告已将 BRx[6] 配置依赖按 descriptor snapshot 顺序证明为无需 runtime mail；本例的 L2 范围也已知且互不混淆。BR 复用不是上述等待的根因。不能直接手删 MAIL，应让编译器证明元数据已经就绪，再重新规划分支内同步。

BatchScalarDmaLoadsPass 能直接做吗？不能，匹配的对象不同

该 Pass 要求单元素暂存、单 DMA writer、单 CT reader，且三者同 block。这里 ids 是四元素 buffer、四个 reader 分散在不同 if；payload 每行 256 B，最终由 ST 消费。把元素数限制放宽不会自动解决跨分支依赖，其地址闭包也不允许任意移动有副作用的 memref.load。

优先方案：复用 parent 的就绪证明

扩展 InjectSync / Staircase：parent 已经确认 metadata 完成，就让这份证明覆盖后续 if 内的同版本读取。检查支配关系、无覆盖写、同一 epoch 和 MAIL 配对。保留原 guard，也避免全 false 时多读 ids。

备选方案：有界的只读 metadata 提前读取

把 C₁ 原型做成独立中端优化：只移动已完整初始化、界内、无后续写入的 metadata 读取。需控制稀疏 mask 的无用读取与寄存器压力，不宜直接改成“所有 LD 都往前排”。

要接近 C₂，还需要第二步。我另试了在 ZeusHigh 中把地址算式也提前，最终汇编与 C₁ 完全相同：descriptor lowering 在各消费点又构造了宽地址运算。正式优化需要保留低层地址计算结果或做有界 CT 调度，并权衡 GPR / BReg 活跃区间、spill 和队列带宽。

C₁ 实验对账：首行前多准备 22 cy，四行搬运阶段从 782 缩到 352 cy（少 430），收尾不变。净省 430 − 22 = 408 cy，kernel 1448 → 1040 cy（−28.2%）。两组 VCS 输出均与 golden 逐字节一致。④自身耗时反而由 114 增至 149 cy，因此应看整段 kernel 收益，不能简单相加单条 LD 时长。

“静态小行数、非末维、连续 payload、单用途 mask”到底限制了什么？
  • 静态小行数：编译时知道要取 4 行；具体取哪行仍由运行时 ids 决定。默认 gather-unroll-limit=16，超过阈值保留循环，0 关闭。16 是策略，不是全局最优证明。
  • 非末维、末维连续：在 [行, 列] 的行维选择数据，一行内元素连续，末维 stride=1 且长度大于 1。
  • 单用途、纯 pointwise mask：每行判断只依赖对应行输入；只接受满足检查的整数比较/布尔运算，不能任意重算共享或有副作用的计算。
  • 动态/大行数、1D/末维 gather、singleton、非连续 payload、scatter 保留原路径；共享或不满足检查的 mask 保留物化。用户外循环不展开。
  • 保留 mask 保护、独立输出分配和填零，不把输入当 scratch。只克隆并删除新生成的 gather loop，不删除仍有消费者的上游 producer。
