01 / 先看 kernel：从 src 任意取四行，写到连续的 dst

ids   = load(row_ids[0:4])
valid = load(flags[0:4]) != 0
result = zeros((4, 128), bf16)
for r in range(4):
    if valid[r]:

G0 / G1 / G2 / G3 对应四行 payload LD，每行 128 个 BF16，即 256 B。S 是最后 1024 B 输出 ST。

主例 K=128、k_offset=0，四个 flag 全有效。实际 kernel 带运行时列边界和 mask；无效行保持 0。MR !986 已展开行循环，本版优化展开后的同步。

02 / 同一个起点、同一个比例：Before 与 After

每条 LD 单独一行，条内直接标指令 ID，右侧给出执行起止 cycle。After 的 G1 在 G0 结束前就开始了；G2、G3 同样重叠。

两组都从 kernel 的 0 开始，横轴同为 0–1448 cy；没有放大短指令。灰底未画出参数搬运、mask/地址计算等操作，不能视为空闲，也不能把条起点当作 dispatch 时刻。

G0–G3：payload LD 执行S：最终输出 ST点击或键盘聚焦色块，比较同一条指令
第一条 LD 只提前 6 cy；主要变化是后面三条不再被重复等待串起来。

省掉的时间能对上账：三段相邻 LD 起点间隔从 223 / 223 / 222 变成 71 / 87 / 87 cy，合计缩短 423 cy；首条提前 6 cy，末条自身多花 9 cy，净省 423 + 6 − 9 = 420 cy。最后 LD→ST 的间隔和 ST 耗时没变。

03 / 只少四对 MAIL，为什么会省这么多？

前面已经执行 P：LD ids → Q：LD flags → R：CT 等待 Q。LD 按序完成，所以 R 通过时 P 也已经完成。分支里的重复等待又排到了前一条 payload LD 后面，反而把下一行卡住。
