01 / 先看 kernel：从 src 任意取四行，写到连续的 dst

ids   = load(row_ids[0:4])
valid = load(flags[0:4]) != 0
result = zeros((4, 128), bf16)
for r in range(4):
    if valid[r]:

G0 / G1 / G2 / G3 对应四行 payload LD，每行 128 个 BF16，即 256 B。S 是最后 1024 B 输出 ST。

主例 K=128、k_offset=0，四个 flag 全有效。实际 kernel 带运行时列边界和 mask；无效行保持 0。MR !986 已展开行循环，本版优化展开后的同步。

02 / 同一个起点、同一个比例：Before 与 After

每条 LD 单独一行，条内直接标指令 ID，右侧给出执行起止 cycle。After 的 G1 在 G0 结束前就开始了；G2、G3 同样重叠。

两组都从 kernel 的 0 开始，横轴同为 0–1448 cy；没有放大短指令。灰底未画出参数搬运、mask/地址计算等操作，不能视为空闲，也不能把条起点当作 dispatch 时刻。

G0–G3：payload LD 执行S：最终输出 ST点击或键盘聚焦色块，比较同一条指令
第一条 LD 只提前 6 cy；主要变化是后面三条不再被重复等待串起来。

省掉的时间能对上账：三段相邻 LD 起点间隔从 223 / 223 / 222 变成 71 / 87 / 87 cy，合计缩短 423 cy；首条提前 6 cy，末条自身多花 9 cy，净省 423 + 6 − 9 = 420 cy。最后 LD→ST 的间隔和 ST 耗时没变。

03 / 只少四对 MAIL，为什么会省这么多？

前面已经执行 P：LD ids → Q：LD flags → R：CT 等待 Q。LD 按序完成，所以 R 通过时 P 也已经完成。分支里的重复等待又排到了前一条 payload LD 后面，反而把下一行卡住。

Before：拿到 G0 完成，才能确认旧 ids 已完成

G0: LD_MOV payload row 0
    CT 读 flag[1]、判断分支
    LD_MAIL SendMails[CT]  ← 排在 G0 后
    CT_MAIL RecvMails[LD]  ← 卡住后续派发
    CT 读 ids[1]、计算地址
G1: LD_MOV payload row 1

After：ids 的可读性由前面已有的 R 证明

G0: LD_MOV payload row 0

    CT 读 ids[1]、计算地址
    ↑ 这部分可与在途 G0 重叠
G1: LD_MOV payload row 1

以上是指令顺序示意，省略其它单元同步。没有移动 CT 读值或 payload LD，没有删除原始 RAW 依赖；只是把四条 ids 依赖归到已有 parent acquire。420 cy 是整条链的实测收益，不能除以 4 当成每对 MAIL 的固定耗时。

05 / C2 实测：LD 排得更密，却把准备时间搬到了最前面

P0–P3 是各行的 flag/id 读取、地址计算和 descriptor 准备；LD0–LD3 对应上面的 G0–G3。上下两组从同一个 kernel 起点 0 开始，比例尺相同。紫色准备阶段包含 CT 读取停顿，黄色是 LD 的实际执行区间。

C1：准备好一行，就提交一行

P0 完成后提交 LD0，接着做 P1、P2、P3。准备后面几行的 CT，可与已经提交的 LD 重叠。

手工 C2：全部准备好，才提交第一条

先完成 P0 → P1 → P2 → P3，再集中提交 LD。CT 工作并没消失，原有 CT 与 LD 的重叠反而减少。mask 保护和必要同步仍保留。

首条晚 251 cy：具体多等了什么？

两版都在 463 cy 完成第 0 行源地址配置。C1 下一拍就配置输出位置，随后是 LD0；C2 此时转去准备其它三行：

C2 在 LD0 前增加的阶段kernel 区间占用时间
P1：第 1 行 flag/id、地址、descriptor464–54783 cy
P2：第 2 行同样准备547–63083 cy
P3：第 3 行同样准备630–71383 cy
LD0 提交前新增比较与跳转713–7152 cy

3 × 83 + 2 = 251 cy。第 0 行输出配置从 464 移到 715 cy，LD0 execute 从 508 移到 759 cy；两边从这条配置到 LD0 execute 的间隔都为 44 cy。首条推迟已能由前移的准备工作解释，不是凭空新增了一次 251 cy 的 LD 同步等待。

每行 83 cy = flag/id 读取及控制流 33 + 宽地址计算 43 + 源 descriptor 配置 7。33 cy 内含两次 CT 从 L2 读取，各到下一条 CT 相隔 13 cy；不是 83 条 CT。

第四条为何没有紧跟前三条？已知事实与未定位边界

C2 的全部 CT 在 744 cy 已结束，四个 VP_MAIL 也在 405/487/570/653 cy 完成；LD2/LD3 仍分别到 771/858 cy 才开始执行。因此这 87 cy 间隔不能归于中间尚未执行的 CT。两份 raw trace 都只有 LD execute/finish，没有 resolve/launch；还不能断定前端实际 dispatch 时间、队列容量或唯一硬件瓶颈。本次停在已有证据，不继续波形定位。

这组实验如何控制变量？

使用保存的 MR !988 实现产物，地址算法不变；各行源 descriptor 分开保存，输出 BR6 位置仍在对应 LD 前设置。每行多两条比较/跳转，动态 CT 从 302 增至 310；保留提前 VP_MAIL，避免把发送后移的影响混进主对照。

一行窗口对照 1032 cy，仅比 C1 多 4 cy；两行窗口 1076 cy；四行窗口 1124 cy。因此不能把四行版慢 96 cy 全归给新增 guard。所有主对照用相同输入、golden，均完整 VCS PASS、1024 B bit-exact、退出 mailbox 全零。

结论与范围：本 MR 只落地 C1。当前“先准备四行再集中提交”的 C2 排布有实测退化，暂不继续。它不证明所有 C2 调度都无收益，也不证明 C1 已达到全局最优；#219 保持独立。
