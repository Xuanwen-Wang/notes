02四个 launch，分别处理什么

当前优化针对 decode 的本地 MoE：输入 X[T,4096] 为 BF16，Router 从 256 个 routed experts 中选择 K=6；每个 EP 持有 64 个 routed experts。此处 FFN 的 I=512 是 TP-local 中间宽度。T 表示当前调用的 token 数，不能据此推断整模型参数规模或端到端批处理效率。

LAUNCH 1RouterX[T,4096]
→ IDs[T,6] INT32
→ probabilities[T,6] FP32
LAUNCH 2Shared FFN输入 QDQ → GateUp
→ SwiGLU / QDQ → Down
→ S[T,4096] BF16
LAUNCH 3Routed FFN本地 expert 有效 route
→ 权重复用与 FFN
→ R[T,6,4096] BF16
LAUNCH 4Reduce本地 slot 升序累加
→ 加入 Shared × 0.25
→ Y[T,4096] BF16

Shared 在计算自己的 FFN 时发布输入 FP8 codes、行 scale 和有效标记；紧接着的 Routed 可以复用这份量化结果。四个主 launch 按 stream 顺序执行，图中的 FFN 子步骤在设备 kernel 内内联，不会再启动另一个 kernel。

“三个 kernel 名字”与“四次 launch”并不矛盾。Shared 与 Routed 共享融合 kernel 入口，通过编译期常量产生不同 specialization；完整链仍是 Router 一次、Shared 一次、Routed 一次、Reduce 一次。通信、加载时 pack、其他模型操作另计。

03保留 DeepSeek 的数值路径，再复用 GLM 的组织方式

新版 DS 的 routed 权重已经是 INT4、沿 K 每 32 个元素一组的 UScale；shared 权重走 FP8 per-channel。因此，早先“act 和 weight 都是 FP8 per-128-K”的理解不适用于当前实现。两条路径都需要保留模型自己的动态激活量化、clamp、SwiGLU 和中间舍入点。源码与 ABI 说明

具体到当前 shape：Routed GateUp scale 为 [64,1024,128]，Down scale 为 [64,4096,16]；Shared 的对应 channel scale 为 [1024] 和 [4096]。动态激活 scale 则分别在完整 H4096 输入行、完整 I512 中间行上计算，不能在分核后各自取局部最大值替代。权重量化源码

加权位置与累加顺序，是两个独立约束

mid = SwiGLU(GateUp(x)) weighted_mid = mid × route_probability q_mid, s_mid = Quantize(weighted_mid) routed = Down(q_mid, s_mid, weight)

上式省略了中间类型转换，仅说明运算位置。把 probability 移到 Down 后面，会跨过动态量化、裁剪和 BF16/FP8 舍入；浮点实数代数上的可交换，不保证这一量化实现等价。Router 默认已经包含 1.5 的 routed scaling，实际调用 Routed 的 factor 为 1.0，不能重复乘 1.5。

Reduce 的要求则是按原 slot 升序做 FP32 累加，最后加入 Shared 并转换为 BF16。它不再接受 route probability。当前优化保留这一顺序，因此每个 token 仍能与独立 staged/reference 路径对齐；以后若改变顺序，应单独建立误差验证。

正常非零量化路径还保留 s = FP32(BF16(maxabs/448))、r = rsqrt(s)，以及两个有序乘法 (v*r)*r 后再转 FP8。这与合成一次 v*(r*r) 或替换为精确除法的舍入不必相同。Gate 使用上界 10，Up 使用 [-10,10]，保留 fast sigmoid 与 BF16 中间舍入；零值及异常值有各自分支。激活量化 helper

04优化怎样从 Python 调用落到设备数据流

第一步：把 FFN 中间结果留在一次 launch 内

原生实现里，输入量化、GateUp、SwiGLU/量化和 Down 分开执行，Shared 和 Routed 各四次，加上 Router 与 Reduce 共十个主 launch。融合之后，两条 FFN 各自执行一次，减少中间全局写回与重复读入。保留独立 reference 实现用于检查中间结果；旧 workspace 参数可兼容调用，但融合路径不会填满 staged 中间 workspace。

第二步：复用输入量化，按专家组织 routed tokens

Shared 已经对同一份 hidden 做了 FP8 输入量化，重复计算没有必要。对于 H4096/I512 的 T16/T24/T32 合格路径，调用方提供三个缓存，Routed 只有在有效标记满足时才复用。异常输入会走保留路径，后续恢复正常输入时重新发布有效缓存。

Routed 把当前核拥有的本地 route 组织成 expert cohort。相同 expert 的多行共享权重读取，每行仍保留自己的 token 来源、scale 和 probability；输出写回原 slot。混合 expert 的 packet 必须保持各自投影，不能仅为了凑满 M 而让 token 使用错误的权重。

第三步：让 M8 调度符合 SRAM 生命周期

T24/T32 的连续 M8 调度保留独立 GateUp 累加缓冲，后续拼接与后处理只在旧消费者完成后复用目标缓冲；T16 使用有界双 packet 调度。这样既能尝试跨 packet 重叠，又避免写入覆盖还在被 PE/VP 读取的数据。Shared T16 延后缓存发布，配合合格的 Down 分块缩短链路。

实现里有两种不同的 M8 组织：稀疏 slot 流可以让一个 packet 包含多个 expert，每行各自投影；owner 分组路径则合并同 expert 行，两个 M8 cohort 的 owner 相同时可共享一次 M16 Down 权重遍历。不能把连续 packet 调度都描述成同 expert batching，也不能将源码顺序等同于硬件已经实现重叠。调度分派

关键不只是“多放几个 buffer”：新 buffer 会增大 SRAM 峰值，可能触发分配器退回更保守的复用方案，重新引入等待。只有最终 native 指令、同步关系和双核时间共同改善，才算有效优化。后面的 Viewer 观察解释了没有采用的候选。

第四步：可选布局减少 GateUp 子块搬运

row_local_n256 把完整 GateUp 投影按 N256 放置，让子块直接写到目标 SRAM tile；INT4 codes、G32 UScale 和 Down 布局保持一致。它以更多权重驻留换取较少搬运，因此保留为显式选择。

Router 和 Reduce 也必须跟着收敛

Router 使用复制权重与 token 分核；Hash 路径直接读取原生 INT32/INT64 IDs，消除调用方额外的 INT64→INT32 cast，仍检查完整整数范围。Reduce 只把本地有效 routes 引入浮点转换和累加，远端空洞允许为 NaN；有界 DMA 区间可能经过中间空洞，但计算不得消费它们。区分“搬运经过”与“计算消费”，才能安全接入有效行优化。

调用关系要稳定，设备 ABI 必须重新生成

Python 旧调用方式保留，不等于旧二进制参数包仍然可用。融合 FFN 增加三个缓存指针；Reduce 增加内部固定 FP32 +1.0 参数以复用 mixed-format VP，它不再重复应用 routed probability。整组代码需要按新源码重新 JIT/AOT。

当前融合 FFN specialization 的运行时 ABI 为 13 个参数、76 bytes、双核执行。新增 SHARED_T16_PIPELINE 是编译期常量，改变 specialization，但不新增 runtime 指针。这个数字用于核对当前版本，不能作为未来所有 specialization 的固定假设。

加载权重并 pack → 预分配 outputs / caches → warmup → capture → replay… → Graph reset └──── 权重 bank、prefix、stride、指针与缓存生命周期保持一致 ────┘

选择布局必须早于加载、warmup 和 capture。pack 只保留选定 bank；不能在捕获后换 prefix/stride、替换底层地址或把 row-local 权重 deepcopy 到新 bank。需要重新分配时，从逻辑 codes/scales 重新 pack，并重新 warmup/capture。

# Set before loading weights and before Graph warmup.
export SGLANG_ZEUS_DSV4_MOE_GATE_LAYOUT=row_local_n256

调用方需要持有三个输出以及可选的三个输入缓存，直到 Graph reset。Shared 与 Routed 必须在同一 stream 顺序执行，hidden 内容必须一致；同一组缓冲不支持并发复用。独立 staged/reference 验证时必须避免环境变量把参考路径替换为融合路径。

三个 PR 保持 draft，用于算法团队接入验证。这里的四 kernel Reduce 只做本地合并，TP/EP 集体通信和模型外围调用不包含在本次性能表里。

更多重叠为什么会更慢

试过的 Shared 候选和 M2 调度候选，虽然局部重叠增加，总耗时分别退化约 10.5% 和 16.1%，所以没有进入当前产品。原因需要结合搬运条数、padding、SRAM 峰值和实际依赖链判断，不能只比较 Viewer 上“颜色是否叠在一起”。

另一次只读分配器分析中，偏好的布局需要 623,200 B，超过可用的 520,192 B，整函数回落到占用 471,744 B 的普通布局；输入、拼接和 QDQ 临时区复用同一地址，形成 WAR 等待。这是后续编译器性能研究的线索，尚不是已经验证的修复或新的编译器 MR。
