01 / IMPLEMENTATION STUDY先看结论：四种 sigmoid 路线，SiLU 另有两种构造方式

当前 API 的名字是 sigmoid 与 silu。sigmoid 有 fast、balanced、accurate、cascade_add 四种公开选择。SiLU 可写成 x × sigmoid(x)，也可以对整个 SiLU 直接分段拟合；这两种做法在精度和指令上都不等价。

FAST

直接查 sigmoid 表

fast64 使用一套非均匀 64 段线性表，含饱和尾部保护；legacy fast32 是另一套表。

BALANCED

两级函数复合

先粗拟合 f(x)，再用 g(f(x)) 修正；两套表在一条 32 lane VP 运算中串接。

ACCURATE

公式分解与修正

exp2 查表重建指数、倒数查表取初值、一次 Newton 修正，再处理负尾部。

CASCADE ADD

独立的残差修正

输出 y₀+h(y₀)。用不同的系数、两次独立 PWL 与显式加法实现。

本次新验证：12 个可编译实现、同一组 512 个 FP32 输入、最终 zbin 反汇编及原生执行字核对；其中 fast64、balanced、accurate、cascade_add、自定义 SiLU 五条路径又经独立 Python 功能仿真器核对，输出逐位一致。没有新增 RTL/VCS、整模精度或真实硬件性能验证。

本页所有“当前”均指 2026-10-30 的固定源码快照。三种主 sigmoid 模式在最小 kernel 中分别是 3 / 3 / 13 条 VP 执行指令；条数包含 PRG 表装载，不包含配置指令。相同条数并不意味着相同吞吐或相同总开销。

03 / IMPLEMENTATION STUDY分段拟合到底存了什么：段数、bank、lane 是三回事

x → 找到区间 i → kᵢ · x + bᵢ

一套线性表存 bp（断点）、k（斜率）、b（截距）。64 段通常用 63 个有效断点；当前标准布局将断点补到 64 个槽位，最后的 sentinel 不参与分段查找。不能把 legacy32 的兼容断点约定和新的自定义 PWLF 输入规范混用。

逻辑函数
64 段→参数打包
两组 32 项→PRG 装表
bp / k / b→数据运算
32 或 64 lane

64 段不等于 64 lane。前者描述函数区间数；后者描述 VP 数据通路。fast64 走普通 64 lane PRG；balanced 使用两组算术模块串接的 32 lane 形式；accurate 的 exp/reciprocal 子链也会使用 L0/L1 模块。

逻辑上一套 64 段 bp/k/b 表占 64×3×4=768 B，两套占 1536 B。但最终 zbin 的 .rodata 还可能同时保留原始表、拼接/交错表、padding，不能直接把这两个数当作最终常量区大小。本次 fast64 的实际常量区为 1536 B，balanced 为 2304 B。

同样，LD_MOV 次数不是“读了几套数学表”：还包含参数与输入 DMA，以及断点/系数 staging。真实表装载要结合 BReg 描述符、PRG load 和最终地址一起看。

04 / IMPLEMENTATION STUDY逐条拆解：四种 sigmoid 算法的差异

fast64：直接拟合 σ(x)

当前实现使用非均匀的 64 段表。负尾部以零斜率段饱和，正尾部饱和到 1。lowering 先做 max(x,-104)，再将 min(x,10) 融入 PWL 运算，避免 ±Inf 在零斜率段产生 0×Inf。它没有在负尾部重新计算真实 exp。

u = max(x, -104)
program_PRG(sigmoid_lut64)
y = PWL(min(u, 10))

legacy fast32 是 [-5,5] 附近的另一套拟合表，且没有上述 fast64 尾部保护。本次在 x=-104 得到 -0.761142，不能认为它只是在 fast64 上减少一半段数。

balanced：两级复合 g(f(x))

program_engine_a(coarse_sigmoid_lut64)
program_engine_b(correction_lut64)
y = g(f(x))  # one VP execution, two serial PRG engines

LUT1 的输入轴是 x，LUT2 的输入轴是粗 sigmoid 的输出 y。第二套表已经编码整个修正映射 g(y)，斜率约为 1，而非单独的残差。因此当前 fused 路线没有末尾额外 +y。

最终配置使用 prg_l0_l1_x；engine A 的 CGFS0=1 与 engine B 的 CGFS1=0 分开设置。前者使用粗 sigmoid 表的对称处理，后者按修正表自身区间查找。两套 64 段表不等于“一张标准 128 段表”，也不承诺 128 段对应的固定精度。

accurate：保留公式结构，用 LUT 加数值修正求值

d      = 1 + exp(-clamp(x, -80, 80))
tail   = exp(clamp(x, -104, -80))
r0     = reciprocal_seed_LUT(d)
c      = 2 - d * r0
r1     = r0 * c
y      = select(x < -80, tail, r1)

exp 通过 t=x·log₂(e)、整数/小数分解 t=n+f，再用 2ⁿ·LUT₂ᶠ(f) 重建。倒数将 d 的指数、尾数分离，查一套 32 段种子表，然后做一次 r₁=r₀(2-dr₀) Newton 修正。

若初值为 r₀=(1+ε)/d，理想实数运算下修正后为 (1-ε²)/d；这说明它能压低倒数初值误差。但 exp 表、FP32 各步舍入及尾部重建仍有误差，accurate 不代表正确舍入的数学精确函数。

负尾部先加相当于二进制指数 +23 的偏移，内部保持正规数，再乘 2⁻²³ 形成 subnormal 结果。本次 x=-100 输出约 3.78e-44，fast64 则输出 0。尾部与选择均以向量执行；即使输入全在普通区间，也不能假定这些指令会被数据相关分支跳过。

cascade_add：另一组系数，显式保留残差加法

program_PRG(lut1_add)
y0 = LUT1_add(x)
program_PRG(lut2_add)
r  = LUT2_add(y0)
y  = y0 + r

前端直接展开为两次 PWL 与一次 arith.addf。两套表使用 approx="no_hoist"，避免共享 PRG 状态被错误重排。它与 balanced 的目标相近，但系数、舍入点、engine 路由、参数搬运都不同，不能承诺两者逐位一致。

需要忽略的旧注释：源码仍有 balanced “两引擎加载同一 placeholder 表”“性能=fast 的 0.5 倍”，以及 accurate “倒数由 rsqrt 平方求出”的历史文字。当前实际分支、生成 IR 与机器码分别证明：balanced 使用不同修正表，accurate 使用向量倒数种子加 Newton。本页不据这些旧注释给性能或精度结论。

05 / IMPLEMENTATION STUDY从 Python 到硬件：哪里变成了真实指令

Python API
approx / seg_num→TTIR
piecewise_linear→Phase A
系数与复合展开→Phase B
VP 模块配方→Phase C
寄存器 / zbin
  1. Python → TTIR：sigmoid 发出带 activation_type="sigmoid"、approx 和 seg_num 的 tt.piecewise_linear。
  2. Phase A：选择系数、将内部数据提升到 FP32、拆分/打包 LUT；cascade_add 在这里展开成复合操作；sigmoid_exp_lut 在这里规范为带用户 exp 表的 accurate。
  3. Phase B：将 PWL 变成 clamp、PRG load、PRG fitter、exp、倒数、Newton、where 等 VP 模块；随后执行 chaining、布局与 buffer 分配等优化。
  4. Phase C：将模块翻译成 VP_SETM_*、VP_SETV_* 等配置，以及 VP_STSR / VP_DTSR 执行指令，配置 BReg，插入 DMA 和同步，最终输出 zbin。

VP_STSR 是单输入向量执行形式，既用于 PRG 装表也用于计算；VP_DTSR 是双输入向量执行形式。Newton 的乘积、修正以及向量 mask 等会引入后者。多个算术模块能放在一次 VP 执行里，不能把“13 个模块名”或“13 个 Python 算术”直接等同于 13 条机器执行指令。

VP_SETM_LUT / CMD / CFS 等负责配置，VP_SETV_* 写入标量常量。它们是真实机器指令，但不与 STSR/DTSR 计为同一类。独立 VP_MAIL / LD_MAIL / CT_MAIL 也要与运算、DMA 分列；本次最小探针没有 VP_MAIL，但指令自身仍可能携带 SendMails/RecvMails。

本次固定 num-vp=1，因此没有将四 lane 拆分、业务循环或多核调度混入主表。对实际业务 kernel，最终数量还受形状、chaining、参数复制、PRG 状态依赖与同步影响。

组合 SiLU 在本次结果中均比对应 sigmoid 多一条 DTSR，用于原始 x 与 sigmoid 输出相乘。业务后面再乘 up 时，额外乘法是否能融合，要以那个 kernel 的最终 IR/ASM 为准。

09 / IMPLEMENTATION STUDY为什么手写 exp 公式也不等价于 accurate

1/(1+exp(-x)) 在数学上是 sigmoid，但通用算子路径可能给出不同的数值与指令实现。本次它没有被识别并替换成专用 accurate 配方。

实编译结果含 exp 的 VP 链、张量除法所需的 rsqrt/SQR 配方和两次 DT transpose；这里的 SQR 配置为 scsq=1。manual-sigmoid 是 12 条 VP 执行、2 条 DT_TRA，模型周期 20048；专用 accurate 则是 13 条 VP 执行、没有 DT_TRA、2143 模型周期。VP 条数更少，反而慢得多，因为运算单元、布局和串行化不同。

该 manual-sigmoid 的最终静态程序还包含后端生成的 CT 循环；本次动态 CT 执行为 231 条，不能把它的静态条数当作动态执行次数。所有已记录 CT / engine 执行字均按重定位后的 zbin PC 核对。

通用 exp 对极端值的处理也不同。本次 manual-silu 在 x=104 的绝对误差约 1.49e-3；不能因为源码用了 exp 和除法就自动标成“精确”。

直接拟合 SiLU 可以省什么

组合 SiLUx → sigmoid LUT → σ̂(x)保留原始 x → 双输入乘法 → x·σ̂(x)
直接 SiLU PWLx → SiLU 专用 LUT → ŝ(x)省掉独立 sigmoid 与乘 x；重新分配拟合误差

组合方案误差近似为 x·δσ(x)；直接 SiLU 拟合优化的是整个输出的误差。若后面还有 up 相乘、BF16/FP8 舍入或 clamp，这些都会改变最终验收指标。不能只用孤立 sigmoid 的误差预算决定 SiLU 的替换。

11 / IMPLEMENTATION STUDY落到业务上，如何选择和验证

选择应以算法验收约束和业务真实输入为依据。fast64、balanced、accurate、直接 SiLU PWL 是不同误差分配和执行结构，替换时需要同时验证函数结果与下游行为。

场景重点验收本次研究能支持什么
Router / TopK专家集合、近分数排序、归一化权重；不能只看 cosine小误差仍可能跨越排序边界；accurate 的开销有实编译依据
KDA 等递推门控多步状态、长序列漂移、门控范围与尾部误差会随 exp 与历史状态传播；需要完整数值 case
Dense / MoE SiLU、SwiGLUclamp、up 相乘、BF16/FP8 舍入、最终输出可比较组合 sigmoid 与直接 SiLU LUT，但不能只验孤立 σ
mHC gate / Sinkhornpre/post gate、归一化、层间传播确认使用 accurate 还是显式 exp 表，分别验证输入域
低精度 IO转换前后值与边界、数据格式内部 FP32 LUT 不等于输出 FP32 精度；本次实测只覆盖 FP32

推荐顺序是：冻结输入及参考精度 → 做正常区间/断点邻域/尾部/特殊值测试 → 验证 Router 或递推等下游行为 → 对比真实 zbin 与执行 trace → 最后再做业务规模的 VCS/RTL 或硬件性能验收。拟合表改变要和编译器调度改变分开做 A/B。

与此前 Router 回退分析相同，显式把 fast 改成 accurate 本身就会改变指令链；仅凭“最近合入了某个编译 MR”不能建立性能归因。本页没有重跑历史 16 行 Router，也没有把历史完整 MoE 数据作为本次结果。
